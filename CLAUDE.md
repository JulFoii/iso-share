# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ISO Share is a minimalistic web application for secure sharing and management of ISO files. It's built as a Node.js Express application with EJS templating, providing both public file viewing and protected admin functionality.

## Key Architecture

- **`server.js`** wires everything together but delegates the non-trivial logic to `lib/`; it stays the place to read for routes and middleware, not for file-format or state-machine details
- **`lib/safe-name.js`**: `safeIsoName()` (filename allowlist) and `safeUploadId()` (UUID check for the chunked-upload session id) — the single validation point every route uses before touching the filesystem or a session file
- **`lib/iso9660.js`**: reads the ISO-9660 Primary Volume Descriptor and El Torito boot catalog straight from the file (no mounting, no external tool) to get volume label, publisher, creation date and BIOS/UEFI bootability. Never throws — a malformed or non-ISO file just yields fewer fields
- **`lib/db.js`**: opens the single SQLite database at `data/iso-share.db` (`node:sqlite`'s `DatabaseSync` — built into Node ≥22.5, not a dependency, in keeping with the project's short-dependency-list rule) and creates every table (`CREATE TABLE IF NOT EXISTS ...`) up front. This is the one place holding everything that used to be scattered JSON files under `data/`, `uploads/.meta/` and `tmp-uploads/`: file metadata, sessions, WebAuthn credentials, the admin password/username, TOTP, the audit log, and chunked-upload session bookkeeping. Only the ISO files themselves — and the in-progress `.part` bytes of a chunked upload — stay on the filesystem; those don't belong in a relational database. `DatabaseSync` is synchronous, opened once at app construction (never inside a request handler); each call from the stores below is a single, indexed operation on a small embedded database (microseconds), not comparable to a blocking `*Sync` call on a multi-GB file
- **`lib/metadata.js`**: per-file row in the `files` table (checksum, ISO info, download counter, tags) — previously a sidecar JSON at `uploads/.meta/<name>.iso.json`. Since `DatabaseSync` is synchronous, no other JS code can run between a read and a write in the same call, so the write-chain serialization and in-memory download-counter buffer the old file-backed store needed are gone: `update()` does a plain read-modify-write, and `recordDownload()` is a single atomic `UPDATE ... SET downloads = downloads + 1`. Tags are a plain `tags: string[]` JSON column, written through the generic merge-`update()` — tags are assigned only by `lib/auto-tags.js` (see below), there is no manual add, so `safeTag()` in `lib/safe-name.js` only guards the candidate strings auto-tags produces and the `:tag` path segment on `DELETE /files/:name/tags/:tag`. `listFiles(query)` (in `server.js`) matches the search term against both name and tags, so `/search`/`/admin-search` and a tag's own badge link double as a tag filter; `server.js`'s `listAllTags()` collects every distinct tag across all files (independent of the current search) for the tag-filter bar in `views/partials/tag-filter.ejs`. `autoTags`/`removedAutoTags` are the bookkeeping fields for `lib/auto-tags.js` — not shown in the UI, just used to reconcile `tags` on the next hash run; `autoTags` is `NULL` (not `[]`) until the first auto-tag run, which is how `scanAll()` tells "never tagged" from "tagged, no candidates". `findByChecksum(sha256)` looks up every filename that already carries a given checksum — the read side of upload dedup (see `lib/chunked-upload.js`), used by `server.js` before a file lands in `uploads/`, not after
- **`lib/auto-tags.js`**: derives tags automatically from the already-parsed ISO info (`BIOS`/`UEFI` bootability, the volume label) — this is the *only* way a file gets tagged; there's no admin form to type one in, deliberately, so a tag always traces back to something read from the ISO itself. Deliberately not guessing an OS/distro name from `volumeId`/`publisher`, since burner-tool strings and inconsistent capitalization would produce more wrong tags than useful ones. `applyAutoTags()` reconciles a sidecar's `tags` with a fresh set of candidates without duplicating what's already there on a rescan, and without resurrecting a tag the admin explicitly removed (tracked in `removedAutoTags`, set by the `DELETE /files/:name/tags/:tag` handler in `server.js` when the removed tag was one of `autoTags`); a changed `volumeId` (re-ripped image) still drops the old auto-tag on the next hash run instead of leaving it stale. Any tag in `tags` that wasn't in the previous `autoTags` (e.g. a leftover from before manual tagging was removed) is left untouched rather than deleted outright
- **`lib/hash-queue.js`**: background, one-at-a-time SHA-256 + ISO-info worker. `scanAll()` runs at startup and picks up files dropped into `uploads/` outside the app (e.g. `rsync`); a checksum is considered stale (and gets recomputed) whenever the file's size/mtime no longer match what was hashed. The same run also (re-)applies auto-tags via `lib/auto-tags.js`, since the ISO info it needs is already being read here. For a file whose checksum is already current but whose row predates the auto-tags feature (`autoTags` still `NULL`), `scanAll()` backfills tags straight from the already-stored `iso` info instead of enqueueing a full rehash — so upgrading to auto-tags doesn't require re-reading every existing upload
- **`lib/chunked-upload.js`**: the resumable-upload protocol (`POST /upload/init`, `PATCH /upload/:id`, `POST /upload/:id/finish`, `DELETE /upload/:id`). Session bookkeeping (name, announced size, creation time) lives in the `upload_sessions` table; only the actual chunk bytes stay as a `.part` file in `tmp-uploads/` — a multi-GB binary doesn't belong in a SQLite row, and the on-disk file size *is* the offset (never a counter mirrored in the DB): the client never tracks progress itself, it re-reads the server's offset after any network error. A `PATCH` whose `Upload-Offset` header doesn't match the real offset is rejected with 409 and the true offset, so the client resyncs instead of corrupting the file. A SHA-256 runs alongside each session's incoming bytes (an in-memory `crypto.Hash` per session, keyed by upload id) so the checksum is known *before* the file is moved into `uploads/` — no second read pass over a multi-GB image just for dedup. `pendingHash()` peeks at it (via `Hash.prototype.copy()`, Node ≥20.12) without finalizing, for `server.js` to check `lib/metadata.js`'s `findByChecksum()` ahead of `finish()`; an exact match under a different name is rejected with 409 before anything is moved. The hasher is best-effort and lives only in process memory — a session resumed after a server restart simply has no hasher, `pendingHash()`/`finish()`'s `sha256` come back `null`, dedup is skipped for that one upload, and the real checksum still arrives via the background hash-queue as always. `replaces` (optional, set at `/upload/init`) is the filename of an existing file the admin explicitly chose to supersede — carried through the session row, never guessed from content or volume label (deliberately, same reasoning as `lib/auto-tags.js` not guessing a distro name); `server.js` deletes that file and its `files` row only *after* the new upload has successfully landed
- **`lib/session-store.js`**: `SqliteSessionStore`, a small `express-session` store backed by the `sessions` table. Replaces the default `MemoryStore`, which lost every session on restart. The old file-backed version needed a write-through cache and a per-session write chain to guard against an async `fs.writeFile`+`rename` being interrupted mid-flight; a synchronous `DatabaseSync` call can't be interleaved with other JS, so both are gone — by the time `set()`/`touch()` call back, the row is already committed
- **`lib/session-secret-store.js`**: the `express-session` signing secret in the `session_secret` table (one row) — deliberately synchronous (unlike every other store here), because it has to be resolved before `app.use(session(...))` in `server.js`, i.e. inside the synchronous `createApp()`, well before the async `start()` ever runs. `ensure(candidate)` returns the already-persisted secret if there is one, otherwise persists and returns `candidate` — the same first-boot-wins bootstrap pattern as the password/username below. Before this existed, an unset `SESSION_SECRET` meant a fresh random secret *every single start*, silently invalidating every session on every restart; this closes that gap regardless of whether the env var is set
- **`lib/move-file.js`**: `rename()` with a `copyFile`+`rm` fallback for `EXDEV`, shared by both the multipart and the chunked-upload finish path
- **`lib/webauthn-store.js`**: the admin's registered passkeys (`webauthn_credentials` table) plus the one stable WebAuthn `userId` (`webauthn_user`, one row) — previously a single-record JSON store at `uploads/.meta/webauthn.json`. Verification itself is `@simplewebauthn/server` (the one deliberate exception to this project's short-dependency-list rule besides `node:sqlite` itself — the crypto involved is too easy to get subtly wrong by hand)
- **`lib/password-store.js`**: persisted admin password as a `scrypt` hash in the `admin_password` table (one row; Node's built-in `crypto.scrypt`, no dependency) — previously `data/admin-password.json`. `start()` bootstraps the row on the very first run if it's still empty: `ADMIN_PASSWORD` if set, otherwise a freshly generated one (logged once). From then on the DB row is permanently authoritative — the same rule as an explicit `/admin-password` change, just triggered automatically instead of requiring one. A later change to `ADMIN_PASSWORD` (or removing it) has no effect once that row exists; delete it (or the whole `data/iso-share.db`) to fall back to the env var again
- **`lib/username-store.js`**: same idea as the password store but for the login username, and much simpler since a username isn't a secret — no hashing, just one row in `admin_username`. `start()` bootstraps it the same way as the password: `ADMIN_USERNAME` if set, otherwise the default `'admin'`, written on the first run so the table is never left empty. `/admin-username` overrides it the same way `/admin-password` overrides the password. Only the password-based `/login` form asks for it; passkey login stays username-less since the credential already identifies the one admin account
- **`lib/totp.js`** / **`lib/totp-store.js`**: TOTP second factor for the password login, hand-implemented (RFC 4226/6238 is a short, stable HMAC-SHA1 spec, not a place like WebAuthn where a hand-rolled implementation risks a subtle bug) instead of adding a dependency. `totp.js` is pure crypto (base32, HOTP, `verifyTotp()` with a ±1-step window, the `otpauth://` URI builder); `totp-store.js` persists the `totp` table (one row: secret) and `totp_recovery_codes` (hashes) the same way `webauthn-store.js` does — previously the single-record `uploads/.meta/totp.json`. No QR code — the setup dialog shows the base32 key as copyable text, since every authenticator app accepts manual entry and a QR library would be a dependency for pure convenience. An in-progress setup lives only in `req.session.totpSetupSecret` until confirmed, so an abandoned setup never leaves a half-enabled second factor
- **`lib/api-token-store.js`**: API-tokens for programmatic access to `/api/v1` (scripts, CI) in the `api_tokens` table — multiple rows per admin, modeled after `lib/webauthn-store.js`. Only `sha256(token)` is stored (indexed, direct `WHERE token_hash = ?` lookup on every `/api/v1` request — safe as a plain indexed lookup since matching it at all requires already knowing the 256-bit token); `createToken()` returns the plaintext token exactly once, the same one-time-reveal pattern as the TOTP recovery codes in `lib/totp-store.js`. A token can only be created by an already-authenticated admin (`POST /admin/api-tokens`, `checkAuth`-gated) — no API path to self-issue one, same bootstrap reasoning as passkeys. Each token carries `scopes: ['read']` and/or `['write']`, checked by `checkApiToken(scope)` in `server.js`
- **`lib/audit-log.js`**: security-relevant events (logins, passkey/TOTP changes, uploads, deletes, password/username changes) in the `audit_log` table — previously an append-only JSON-Lines file at `data/audit.log`. Trimmed to the newest `keepRowsOnTrim` rows once the row count passes `maxRows` (defaults 15,000/20,000), so it never grows unbounded — the row-count equivalent of the old byte-size trim. A logging failure is swallowed — it must never fail the action it's logging
- **`lib/migrate-legacy.js`**: one-time import of the pre-SQLite JSON state (file sidecars, `admin-password.json`, `admin-username.json`, `webauthn.json`, `totp.json`, `audit.log`, and any in-flight chunked-upload sessions under `tmp-uploads/`) into the database, run from `start()` before anything else. Each piece only imports into an *empty* table, so a second start never double-imports. After a successful import, the source file is deleted (and `uploads/.meta/` removed once empty) — the database is meant to be the sole, lasting home for this data, not a copy that drifts from a JSON file left sitting next to it. Sessions (express-session) are deliberately not migrated: they're ephemeral, so one re-login after the upgrade is an acceptable cost, and `data/sessions/` (if left over from before this change) is never touched
- **`lib/zip-stream.js`**: hand-rolled streaming ZIP writer (`writeZip()`) for the bulk-download route, store method only (no compression — ISOs barely compress anyway) with a data descriptor per entry, so it never needs to know a file's CRC32/size before streaming it straight from disk into the response. Deliberately no Zip64: `fitsInClassicZip()` lets `server.js` reject a selection whose per-file or total size would overflow the classic 32-bit fields *before* the stream starts, rather than emit a truncated/corrupt archive
- **Express-based**: Uses Express.js with EJS templating for server-side rendering
- **Session-based auth**: Simple password authentication with express-session, session state persisted via `SqliteSessionStore` (see above)
- **File management**: multipart upload (`/upload`, no-JS fallback) and a resumable chunked-upload protocol (`/upload/init` + friends, what `upload.js` actually uses) both land in `uploads/` through `lib/move-file.js`
- **Two-tier access**: Public file listing/download and admin upload/delete functionality
- **Frontend**: No CSS/JS framework and no CDN — everything is served from `public/`. `public/css/tokens.css` holds the design tokens (dark is the default, `[data-theme="light"]` overrides), `public/css/main.css` the components. The scripts in `public/js/` are small self-contained IIFEs wired up declaratively via `data-*` attributes, so a view opts into behaviour by adding markup, not by adding a script tag. `views/partials/file-row.ejs` renders one file's row + its collapsible detail row (checksum, verify snippet, boot info) and is shared by `index.ejs` and `admin.ejs`
- **Progressive enhancement is load-bearing**: the newer platform features (cross-document view transitions, `@starting-style`, scroll-driven `.reveal` animations, Popover API + anchor positioning) are all layered so an unsupporting browser gets the static version instead of a broken one. Two guards must stay: the `.reveal` rules live inside `@supports (animation-timeline: view())` because their `opacity: 0` start frame would otherwise hide the cards permanently, and `@supports not selector(:popover-open)` hides the theme menu so it can't sit invisible over the nav (`theme.js` then falls back to cycling on click). The detail row starts `[hidden]` server-side and only opens via `row-details.js`, so a no-JS client still gets the checksum through `/checksums`

### File Operations
- Files are stored in the `uploads/` directory; per-file metadata (checksum, ISO info, download count) lives in the `files` table of the SQLite database at `data/iso-share.db` (see `lib/db.js`)
- Only `.iso` files are accepted for upload
- **Bootstrap-once env vars** — `ADMIN_PASSWORD`, `ADMIN_USERNAME`, `SESSION_SECRET`: each is read only until its row in the database exists, which `start()` guarantees happens on the very first run (generating a value where there's no sane default, namely the password and the session secret). After that the DB row is what counts, permanently — changing or removing the env var later does nothing, the same as an explicit change via `/admin-password`/`/admin-username` would. This is deliberate: a secret that lives forever in an env var (`.env`, `docker-compose.yml`, shell history, `docker inspect`) is worse operational practice than one written once to the app's own database. To force a fresh bootstrap from the env var again, delete the corresponding row (or all of `data/iso-share.db`) — see "Inspecting the database" below for how
- `MAX_FILE_SIZE_MB` (default 8192) caps both the multipart and the chunked-upload path — a plain runtime cap, not a secret, so it stays an env var read fresh on every start; there's no admin-UI route to change it, unlike password/username
- `DATA_DIR` (default `data/`) is where the SQLite database (`iso-share.db`, plus its `-wal`/`-shm` files) lives — sessions, file metadata, passkeys, admin password/username, the session secret, TOTP and the audit log all live in it. Mount this as a volume in Docker, not `/tmp`. This one **can't** move into the database itself for the obvious circular reason (it says where the database is)
- `TRUST_PROXY` and `NODE_ENV` also stay env-only, but for a different reason than `DATA_DIR`: they're trust decisions about the deployment environment itself (is there a real reverse proxy overwriting `X-Forwarded-For`? is this production?), which have to be fixed *before* any request — let alone any database row an admin could edit through the UI — is allowed to influence how the server interprets one. Making either one DB-editable from inside the app would let a web-reachable setting flip a trust boundary that's supposed to be decided by whoever controls the deployment, not by the app itself

### Inspecting the database
There's no separate DB server to connect to — `data/iso-share.db` is a plain SQLite file, safely readable while the app is running (WAL mode, see `lib/db.js`):
```bash
node -e "
const { DatabaseSync } = require('node:sqlite');
const db = new DatabaseSync('./data/iso-share.db', { readOnly: true });
console.log(db.prepare('SELECT name, downloads, sha256 FROM files').all());
db.close();
"
```
For point-and-click browsing, "DB Browser for SQLite" (free, cross-platform) or a `.db`-viewer extension for the editor works too — open read-only while the server is running. Table names match the schema in `lib/db.js`. Writing to the DB by hand while the server runs is best avoided (go through the app's routes instead, so things like auto-tags/checksums stay consistent) — reading is always safe.

## Key Routes Structure

- `/` - Public file listing with search and download
- `/checksums` - `SHA256SUMS` (coreutils format) for every file with a current checksum
- `/api/files.json` - JSON equivalent of the file listing (same fields as the index page/`describe()`, honors `?q=` like `/search`), for scripts/CI/monitoring; public like `/checksums`, since it exposes nothing the listing doesn't already show
- `/api/tags.json` - JSON list of every tag currently in use, independent of any search — the same set `listAllTags()` feeds to the tag-filter bar
- `/healthz` - liveness endpoint for the Docker healthcheck; deliberately not `/`, which would render the whole listing every 30s
- `/metrics` - Prometheus text-format counters (file count, storage bytes, downloads; uploads/deletes/login counters derived from the audit log, so they're only as complete as that log's trim window). Public like `/healthz` — the numbers reveal nothing the public listing doesn't already show
- `/files/:name/tags/:tag` (`DELETE`) - Admin-only removal of a single tag from a file (see `lib/metadata.js`). There is no route to add one: tags are assigned exclusively by `lib/hash-queue.js`/`lib/auto-tags.js` from the ISO itself (bootability, volume label) as part of the background hash run. Removing is JS-only via `public/js/tags.js`, the same precedent as `/webauthn/credentials/:id` and `/delete-bulk`; if the removed tag was an auto-tag it's recorded in `removedAutoTags` so the next rescan doesn't reattach it. `/` and `/admin-upload` also show a tag-filter bar (`views/partials/tag-filter.ejs`, driven by `listAllTags()` in `server.js`) listing every tag in use, and the search box grows a reset link back to the unfiltered listing whenever a query is active
- `/login` - Admin authentication (password, plus an optional passkey via `/webauthn/login/options` + `/webauthn/login/verify`, same rate limiters as the password form). A password login with TOTP enabled redirects to `/login/totp` instead of setting up the session directly
- `/login/totp` - Second factor after a successful password login (`req.session.pendingTotp`); accepts a 6-digit TOTP code or a recovery code, same rate limiters as `/login`. Not required after a passkey login, which already counts as MFA-equivalent
- `/admin-upload` - Protected admin area for file management, including passkey registration (`/webauthn/register/options` + `/webauthn/register/verify`) and management (`GET`/`DELETE /webauthn/credentials`)
- `/admin-password` - Change the admin password (admin only, no old-password re-entry — see `lib/password-store.js`)
- `/admin-username` - Change the admin username (admin only, used by the password login form; not by passkey login — see `lib/username-store.js`)
- `/totp/setup`, `/totp/confirm`, `/totp/disable` - Set up/confirm/disable the TOTP second factor (admin only, see `lib/totp-store.js`); `/totp/confirm` returns a set of one-time recovery codes exactly once
- `/admin-audit-log` - Full audit log (admin only); `admin.ejs` also shows the latest few entries inline, see `lib/audit-log.js`
- `/upload` - Multipart file upload endpoint, admin only (no-JS fallback; `upload.js` prefers the chunked protocol below). Same dedup/replace rules as the chunked path below, just checked synchronously against the already-saved temp file instead of a streaming hash
- `/upload/init`, `/upload/:id` (GET/PATCH/DELETE), `/upload/:id/finish` - Resumable chunked-upload protocol, admin only (see `lib/chunked-upload.js`). `/upload/init` takes an optional `replaces` field (an existing filename the admin picked in `admin.ejs`'s upload form to supersede); `/upload/:id/finish` rejects with 409 if the upload's content is an exact checksum duplicate of a *different* existing file, and — on success — deletes the `replaces` target (file + `files` row) and logs `upload_replaced`
- `/delete` - File deletion endpoint (admin only), also removes the file's row from the `files` table
- `/download-zip` - Bulk download of several selected files as one streamed ZIP (public, same rate limiter as `/download`; see `lib/zip-stream.js`). Silently skips names that no longer exist, rejects a selection over `MAX_BULK_FILES` (100) or one that would overflow the classic ZIP format's 32-bit size fields
- `/delete-bulk` - Bulk deletion of several selected files in one request (admin only), same name validation and `MAX_BULK_FILES` cap as `/download-zip`
- `/search` and `/admin-search` - Real-time file filtering
- `/api/v1/*` - Versioned JSON API for scripts/CI, see `lib/api-token-store.js`. Read endpoints (`GET /api/v1/files`, `/files/:name`, `/tags`, `/checksums`) are public and paginated (`page`/`perPage`, capped at 200), same reasoning as `/api/files.json`; `GET /api/v1/files` also takes `?tag=`/`?sort=`. Write endpoints (`POST/PATCH/DELETE /api/v1/uploads*` — same protocol as `/upload/init` and friends, just token-gated —, `DELETE /api/v1/files/:name`, `POST /api/v1/files/bulk-delete`, `DELETE /api/v1/files/:name/tags/:tag`) and `GET /api/v1/audit-log` require an `Authorization: Bearer <token>` header via `checkApiToken('read'|'write')`, completely independent of the session — a logged-in browser session carries no authority on this path. Responses use a `{ data, meta? }` / `{ error, code }` envelope, unlike the legacy `/api/*.json` routes which stay unversioned/unchanged for backward compatibility. Documented in `public/openapi.json` (hand-written OpenAPI 3.0, no `swagger-ui-express` dependency)
- `/admin/api-tokens` (`GET`/`POST`) and `/admin/api-tokens/:id` (`DELETE`) - `checkAuth`-gated creation/listing/revocation of `/api/v1` tokens (see `lib/api-token-store.js`); the plaintext token is only ever in the `POST` response, never again afterward

## Security

`server.js` is hardened against the common web risks; keep these in place when editing:
- **Secrets**: no functional defaults — `ADMIN_PASSWORD`/`SESSION_SECRET` are random-generated if unset, and either way (set or generated) persisted to the database on the very first `start()` (see "Bootstrap-once env vars" above). The password is compared timing-safe via SHA-256 + `crypto.timingSafeEqual` before a persisted hash exists, `scrypt` after
- **helmet** sets CSP (`'self'` only, `data:` for images), `frame-ancestors 'none'`, `nosniff`, `same-origin` referrer policy; `x-powered-by` is disabled
- **CSRF**: `sameSite: 'strict'` cookie plus a same-origin (Origin/Referer host == Host) check on every POST/PUT/PATCH/DELETE
- **Session**: `httpOnly`, `sameSite: 'strict'`, `secure` when prod or behind a proxy; regenerated on login (anti-fixation). Cookie name `iso.sid`, backed by `SqliteSessionStore` (`lib/session-store.js`), not the default in-memory store. `TRUST_PROXY` numeric = hop count. The cookie's own `maxAge` (24h) is a fixed absolute ceiling from login, separate from the idle timeout below
- **Admin idle timeout**: `checkAuth` in `server.js` tracks `req.session.lastActivity` and destroys the session (DB row + cookie) the first time a logged-in admin makes a request more than `ADMIN_IDLE_TIMEOUT_MS` (10 minutes) after their last one, redirecting to `/login?idle=1` (or a JSON 401 for API-style callers) instead of `next()`. This is independent of the 24h cookie `maxAge` above — an idle admin is logged out long before that absolute ceiling — and only ever checked/updated on `checkAuth`-gated routes, not on every request. Overridable via the `adminIdleTimeoutMs` option to `createApp()` for tests; logged to the audit log as `session_idle_timeout`. `public/js/idle-timer.js` mirrors this bank-style in the UI: a countdown badge next to "Abmelden" in `partials/navbar.ejs` (reads the timeout from `app.locals.adminIdleTimeoutMs`, wired into every render), reset to the full window by real click/key/mouse/touch activity, which — throttled to at most once/minute — also pings `GET /admin/ping` (`checkAuth`-gated, no-op body) to keep the *actual* server-side session alive; hitting zero client-side navigates to `/logout`. `heartbeat.js`'s automatic 20s poll of `/admin/partials/listing` is deliberately exempted from extending `lastActivity` (via the `X-Idle-Background` request header, checked in `checkAuth`) — otherwise a tab merely left open, with nobody at the keyboard, would keep the session alive forever and defeat the whole feature
- **Rate limit**: `express-rate-limit` on `/login` (10 / 15 min, plus a global backstop — see below) and on `/download` (60 / min per IP; range requests aren't double-counted as separate downloads)
- **Filename safety**: `safeIsoName()` (basename + allowlist regex + `.iso`) guards `/upload`, `/delete`, `/download` and the chunked-upload's `name` field; `safeUploadId()` guards the `:id` path param on every `/upload/:id*` route
- **Uploads**: `uploads/` is NOT served statically — only via `/download` with type check; multer temp dir and the chunked-upload `.part` files (session bookkeeping is a DB row, see `lib/chunked-upload.js`) live in `tmp-uploads/` (outside web root), both capped by `MAX_FILE_SIZE_MB`. Checksums, download counts and every other credential/metadata table live in `data/iso-share.db`, entirely outside `uploads/` and never served directly
- Errors are caught by a final handler that never leaks stack traces
- **All request-path filesystem access is async** (`fs/promises`); no `*Sync` call runs inside a handler, so a large `uploads/` can't block the event loop. The upload move uses `rename` with a `copyFile`+`rm` fallback for `EXDEV` (temp dir and `uploads/` on different mounts, e.g. a Docker bind mount) — see `lib/move-file.js`
- **Login brute-force** is capped two ways: per-IP (`express-rate-limit`, failures only) and a global backstop keyed to a constant, so a spoofed `X-Forwarded-For` (when `TRUST_PROXY` is set without a real proxy) can't mint fresh buckets. Only enable `TRUST_PROXY` behind a proxy that overwrites `X-Forwarded-For`
- **Chunked-upload protocol**: a `PATCH` is only accepted when its `Upload-Offset` header equals the session's real on-disk offset, and the server never writes more bytes than the size announced at `init` — both close off ways a client could otherwise corrupt or oversize the assembled file
- **Passkeys**: additive, not a replacement — the password form is always the fallback. A passkey can only be registered by an already-authenticated admin (no separate bootstrap route); `/webauthn/login/options` and `/webauthn/login/verify` are public but share the exact same `loginLimiterGlobal`/`loginLimiterPerIp` instances as `/login`, so an attacker can't double their brute-force budget by alternating routes. `rpID`/`expectedOrigin` are derived per-request from `req.get('host')`/`req.protocol` (same inputs as the CSRF `sameOrigin` check) rather than a separate env var — a passkey is therefore bound to the hostname it was registered under
- **Password change** (`/admin-password`): checkAuth-gated only, deliberately without re-entering the current password — the whole point is recovering from a forgotten one, and a valid session already implies full admin access regardless. Hashed with `scrypt` (salted, promisified so it doesn't block the event loop), not the plain `SHA-256` used for the `ADMIN_PASSWORD` env-var comparison — that one is fine unsalted since it's not user-chosen/persisted, but a user-settable password gets the stronger, deliberately slow KDF
- **Username check** (`/login`): a wrong username and a wrong password get the exact same generic error ("Benutzername oder Passwort falsch") — distinguishing them would let an attacker enumerate the username. `passwordMatches()` is always awaited even when the username is already known to be wrong, so a mismatched username can't be inferred from a faster response. Both `/admin-password` and `/admin-username` share the same async-form + `<dialog>`-modal pattern in `public/js/account-forms.js`, with a plain-form no-JS fallback (inline error / silent redirect) preserved for both
- **TOTP second factor**: the session is regenerated right after the *first* factor (password) succeeds, before `/login/totp` is even reached — an attacker who somehow knew the pre-login session id can't ride it through to a fully authenticated session just because TOTP was still pending. `/login/totp` and `/totp/confirm` share the exact same rate limiters as `/login`, for the same anti-doubling reason as the passkey routes. Recovery codes are single-use, checked with a `timingSafeEqual` loop, and hashed with plain SHA-256 rather than `scrypt` — unlike the admin password they're server-generated and already high-entropy, so a slow KDF buys nothing (same reasoning as `PASSWORD_HASH` for the env-var password)
- **Bulk routes** (`/download-zip`, `/delete-bulk`): every name in the `{ names: [...] }` body goes through the exact same `safeIsoName()` as the single-file routes — a batch of names is not a new trust boundary. `/download-zip` stays public (like `/download`) and shares its rate limiter; `/delete-bulk` is `checkAuth`-gated like `/delete`
- **`/api/v1` token auth**: completely separate trust boundary from the session — `checkApiToken()` never reads `req.session`, so a stolen/forged session cookie grants zero `/api/v1` authority, and a leaked token grants zero session/admin-UI access either way. A token is created only via `POST /admin/api-tokens` (`checkAuth`-gated, no API-reachable self-issue path, same bootstrap reasoning as passkeys) and carries `scopes: ['read']`/`['write']` checked per route. Because of this separation, the global CSRF `sameOrigin` check is skipped for `/api/v1/*` — a cross-site request riding the victim's cookie still can't produce a valid `Authorization: Bearer` header, so the check would only false-positive-block legitimate script/CI clients that don't send a same-origin `Origin`/`Referer`. Failed token checks share a login-style two-tier rate limiter (`apiAuthLimiterPerIp`/`apiAuthLimiterGlobal`, defense-in-depth — a 256-bit token isn't brute-forceable); all of `/api/v1` additionally shares one generous `apiLimiter` (300/min) against runaway scripts. Error responses carry a stable `code` field (`missing_token`, `invalid_token`, `insufficient_scope`, `not_found`, …) alongside the German `error` message, and the 404/500 handlers branch to JSON for any `/api/v1/*` path instead of the plaintext used elsewhere
