# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ISO Share is a minimalistic web application for secure sharing and management of ISO files. It's built as a Node.js Express application with EJS templating, providing both public file viewing and protected admin functionality.

## Key Architecture

- **`server.js`** wires everything together but delegates the non-trivial logic to `lib/`; it stays the place to read for routes and middleware, not for file-format or state-machine details
- **`lib/safe-name.js`**: `safeIsoName()` (filename allowlist) and `safeUploadId()` (UUID check for the chunked-upload session id) — the single validation point every route uses before touching the filesystem or a session file
- **`lib/iso9660.js`**: reads the ISO-9660 Primary Volume Descriptor and El Torito boot catalog straight from the file (no mounting, no external tool) to get volume label, publisher, creation date and BIOS/UEFI bootability. Never throws — a malformed or non-ISO file just yields fewer fields
- **`lib/db.js`**: opens the single SQLite database at `data/iso-share.db` (`node:sqlite`'s `DatabaseSync` — built into Node ≥22.5, not a dependency, in keeping with the project's short-dependency-list rule) and creates every table (`CREATE TABLE IF NOT EXISTS ...`) up front. This is the one place holding everything that used to be scattered JSON files under `data/`, `uploads/.meta/` and `tmp-uploads/`: file metadata, sessions, WebAuthn credentials, the admin password/username, TOTP, the audit log, and chunked-upload session bookkeeping. Only the ISO files themselves — and the in-progress `.part` bytes of a chunked upload — stay on the filesystem; those don't belong in a relational database. `DatabaseSync` is synchronous, opened once at app construction (never inside a request handler); each call from the stores below is a single, indexed operation on a small embedded database (microseconds), not comparable to a blocking `*Sync` call on a multi-GB file. Connection pragmas: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`. **Schema changes are versioned** via `PRAGMA user_version`: `MIGRATIONS` is an append-only, numbered list; `applyMigrations()` runs each pending one in its own `BEGIN IMMEDIATE` transaction together with bumping the version, so a failed migration leaves the previous consistent state. New *tables* may still go into `SCHEMA` as `CREATE TABLE IF NOT EXISTS`, but anything that alters an existing table (`ALTER TABLE`, data rewrites) must be a new migration entry — never edit or renumber an existing one. A database whose `user_version` is higher than the code knows (rollback to an older image) is refused with `code: 'schema_too_new'` instead of being used with a stale schema. `maintainDatabase()` (`PRAGMA optimize` + passive WAL checkpoint) runs hourly from `server.js`
- **`lib/metadata.js`**: per-file row in the `files` table (checksum, ISO info, download counter, tags) — previously a sidecar JSON at `uploads/.meta/<name>.iso.json`. Since `DatabaseSync` is synchronous, no other JS code can run between a read and a write in the same call, so the write-chain serialization and in-memory download-counter buffer the old file-backed store needed are gone: `update()` does a plain read-modify-write, and `recordDownload()` is a single atomic `UPDATE ... SET downloads = downloads + 1`. Tags are a plain `tags: string[]` JSON column, written through the generic merge-`update()` — tags are assigned only by `lib/auto-tags.js` (see below), there is no manual add, so `safeTag()` in `lib/safe-name.js` only guards the candidate strings auto-tags produces and the `:tag` path segment on `DELETE /files/:name/tags/:tag`. `listFiles(query)` (in `server.js`) matches the search term against both name and tags, so `/search`/`/admin-search` and a tag's own badge link double as a tag filter; `server.js`'s `listAllTags()` collects every distinct tag across all files (independent of the current search) for the tag-filter bar in `views/partials/tag-filter.ejs`. `autoTags`/`removedAutoTags` are the bookkeeping fields for `lib/auto-tags.js` — not shown in the UI, just used to reconcile `tags` on the next hash run; `autoTags` is `NULL` (not `[]`) until the first auto-tag run, which is how `scanAll()` tells "never tagged" from "tagged, no candidates". `findByChecksum(sha256)` looks up every filename that already carries a given checksum — the read side of upload dedup (see `lib/chunked-upload.js`), used by `server.js` before a file lands in `uploads/`, not after
- **`lib/auto-tags.js`**: derives tags automatically from the already-parsed ISO info (`BIOS`/`UEFI` bootability, the volume label) — this is the *only* way a file gets tagged; there's no admin form to type one in, deliberately, so a tag always traces back to something read from the ISO itself. Deliberately not guessing an OS/distro name from `volumeId`/`publisher`, since burner-tool strings and inconsistent capitalization would produce more wrong tags than useful ones. `applyAutoTags()` reconciles a sidecar's `tags` with a fresh set of candidates without duplicating what's already there on a rescan, and without resurrecting a tag the admin explicitly removed (tracked in `removedAutoTags`, set by the `DELETE /files/:name/tags/:tag` handler in `server.js` when the removed tag was one of `autoTags`); a changed `volumeId` (re-ripped image) still drops the old auto-tag on the next hash run instead of leaving it stale. Any tag in `tags` that wasn't in the previous `autoTags` (e.g. a leftover from before manual tagging was removed) is left untouched rather than deleted outright
- **`lib/hash-queue.js`**: background, one-at-a-time SHA-256 + ISO-info worker. `scanAll()` runs at startup and picks up files dropped into `uploads/` outside the app (e.g. `rsync`); a checksum is considered stale (and gets recomputed) whenever the file's size/mtime no longer match what was hashed. The same run also (re-)applies auto-tags via `lib/auto-tags.js`, since the ISO info it needs is already being read here. For a file whose checksum is already current but whose row predates the auto-tags feature (`autoTags` still `NULL`), `scanAll()` backfills tags straight from the already-stored `iso` info instead of enqueueing a full rehash — so upgrading to auto-tags doesn't require re-reading every existing upload
- **`lib/chunked-upload.js`**: the resumable-upload protocol (`POST /upload/init`, `PATCH /upload/:id`, `POST /upload/:id/finish`, `DELETE /upload/:id`). Session bookkeeping (name, announced size, creation time) lives in the `upload_sessions` table; only the actual chunk bytes stay as a `.part` file in `tmp-uploads/` — a multi-GB binary doesn't belong in a SQLite row, and the on-disk file size *is* the offset (never a counter mirrored in the DB): the client never tracks progress itself, it re-reads the server's offset after any network error. A `PATCH` whose `Upload-Offset` header doesn't match the real offset is rejected with 409 and the true offset, so the client resyncs instead of corrupting the file. A SHA-256 runs alongside each session's incoming bytes (an in-memory `crypto.Hash` per session, keyed by upload id) so the checksum is known *before* the file is moved into `uploads/` — no second read pass over a multi-GB image just for dedup. `pendingHash()` peeks at it (via `Hash.prototype.copy()`, Node ≥20.12) without finalizing, for `server.js` to check `lib/metadata.js`'s `findByChecksum()` ahead of `finish()`; an exact match under a different name is rejected with 409 before anything is moved. The hasher is best-effort and lives only in process memory — a session resumed after a server restart simply has no hasher, `pendingHash()`/`finish()`'s `sha256` come back `null`, dedup is skipped for that one upload, and the real checksum still arrives via the background hash-queue as always. `replaces` (optional, set at `/upload/init`) is the filename of an existing file the admin explicitly chose to supersede — carried through the session row, never guessed from content or volume label (deliberately, same reasoning as `lib/auto-tags.js` not guessing a distro name); `server.js` deletes that file and its `files` row only *after* the new upload has successfully landed
- **`lib/session-store.js`**: `SqliteSessionStore`, a small `express-session` store backed by the `sessions` table. Replaces the default `MemoryStore`, which lost every session on restart. The old file-backed version needed a write-through cache and a per-session write chain to guard against an async `fs.writeFile`+`rename` being interrupted mid-flight; a synchronous `DatabaseSync` call can't be interleaved with other JS, so both are gone — by the time `set()`/`touch()` call back, the row is already committed
- **`lib/session-secret-store.js`**: the `express-session` signing secret in the `session_secret` table (one row) — deliberately synchronous (unlike every other store here), because it has to be resolved before `app.use(session(...))` in `server.js`, i.e. inside the synchronous `createApp()`, well before the async `start()` ever runs. `ensure(candidate)` returns the already-persisted secret if there is one, otherwise persists and returns `candidate` — the same first-boot-wins bootstrap pattern as the password/username below. Before this existed, an unset `SESSION_SECRET` meant a fresh random secret *every single start*, silently invalidating every session on every restart; this closes that gap regardless of whether the env var is set
- **`lib/db-tx.js`**: `transaction(db, fn)` — nestable transaction for a `DatabaseSync`: the outermost level is `BEGIN`/`COMMIT`, inner levels are `SAVEPOINT`s (depth tracked per db in a `WeakMap`, since `db.isTransaction` needs Node 22.16 and the floor is 22.5). `fn` must be synchronous. `createTicket()`/`addReply()`/`addNote()` in `lib/ticket-store.js` use it so `lib/attachment-store.js` `commit()` can wrap them together with the attachment rows
- **`lib/inbound-mail-store.js`**: bookkeeping for inbound mail in three small tables — `inbound_mail_seen` (`claim(key)`: atomic `INSERT OR IGNORE`, first processing wins), `inbound_mail_notices` (`notifyOnce(key, windowMs)` for throttled automatic notices) and `imap_state` (UID progress per mailbox). `prune()` drops entries older than 90 days, hourly from `runMaintenance()`
- **`lib/move-file.js`**: `rename()` with a `copyFile`+`rm` fallback for `EXDEV`, shared by both the multipart and the chunked-upload finish path
- **`lib/webauthn-store.js`**: the admin's registered passkeys (`webauthn_credentials` table) plus the one stable WebAuthn `userId` (`webauthn_user`, one row) — previously a single-record JSON store at `uploads/.meta/webauthn.json`. Verification itself is `@simplewebauthn/server` (the first of two deliberate exceptions to this project's short-dependency-list rule besides `node:sqlite` itself — the crypto involved is too easy to get subtly wrong by hand; `nodemailer`, see `lib/mailer.js`, is the second)
- **`lib/password-store.js`**: persisted admin password as a `scrypt` hash in the `admin_password` table (one row; Node's built-in `crypto.scrypt`, no dependency) — previously `data/admin-password.json`. `start()` bootstraps the row on the very first run if it's still empty: `ADMIN_PASSWORD` if set, otherwise a freshly generated one (logged once). From then on the DB row is permanently authoritative — the same rule as an explicit `/admin-password` change, just triggered automatically instead of requiring one. A later change to `ADMIN_PASSWORD` (or removing it) has no effect once that row exists; delete it (or the whole `data/iso-share.db`) to fall back to the env var again
- **`lib/username-store.js`**: same idea as the password store but for the login username, and much simpler since a username isn't a secret — no hashing, just one row in `admin_username`. `start()` bootstraps it the same way as the password: `ADMIN_USERNAME` if set, otherwise the default `'admin'`, written on the first run so the table is never left empty. `/admin-username` overrides it the same way `/admin-password` overrides the password. Only the password-based `/login` form asks for it; passkey login stays username-less since the credential already identifies the one admin account
- **`lib/totp.js`** / **`lib/totp-store.js`**: TOTP second factor for the password login, hand-implemented (RFC 4226/6238 is a short, stable HMAC-SHA1 spec, not a place like WebAuthn where a hand-rolled implementation risks a subtle bug) instead of adding a dependency. `totp.js` is pure crypto (base32, HOTP, `verifyTotp()` with a ±1-step window, the `otpauth://` URI builder); `totp-store.js` persists the `totp` table (one row: secret) and `totp_recovery_codes` (hashes) the same way `webauthn-store.js` does — previously the single-record `uploads/.meta/totp.json`. No QR code — the setup dialog shows the base32 key as copyable text, since every authenticator app accepts manual entry and a QR library would be a dependency for pure convenience. An in-progress setup lives only in `req.session.totpSetupSecret` until confirmed, so an abandoned setup never leaves a half-enabled second factor
- **`lib/api-token-store.js`**: API-tokens for programmatic access to `/api/v1` (scripts, CI) in the `api_tokens` table — multiple rows per admin, modeled after `lib/webauthn-store.js`. Only `sha256(token)` is stored (indexed, direct `WHERE token_hash = ?` lookup on every `/api/v1` request — safe as a plain indexed lookup since matching it at all requires already knowing the 256-bit token); `createToken()` returns the plaintext token exactly once, the same one-time-reveal pattern as the TOTP recovery codes in `lib/totp-store.js`. A token can only be created by an already-authenticated admin (`POST /admin/api-tokens`, `checkAuth`-gated) — no API path to self-issue one, same bootstrap reasoning as passkeys. Each token carries `scopes: ['read']` and/or `['write']`, checked by `checkApiToken(scope)` in `server.js`
- **`lib/event-store.js`**: the central event log — every event of the app (audit actions, every HTTP request, background jobs, slow queries/DB errors, rate-limit blocks, CSRF rejections, log messages) as one row in its **own** SQLite file `DATA_DIR/events.db`, deliberately separate from `iso-share.db`: log volume doesn't compete for the main DB's write lock, `VACUUM INTO` backups don't bloat, and restoring a backup doesn't roll the log back (the restore itself stays recorded). `record()` builds the row synchronously — context (actor, IP, user agent, request id, method/path, `session_hash` = truncated SHA-256 of the session id, never the id itself) comes from the request via `AsyncLocalStorage` (`events.middleware()` in `server.js`), or from an explicit `req` — and queues it; a timer (`flushIntervalMs`, 250 ms) or `batchSize` writes the queue in one transaction, so no request ever waits on the log. Audit rows and `CRITICAL` are flushed immediately. The queue is bounded: on overflow DEBUG/INFO are dropped (counted, `/metrics`), WARNING+ never. `events_hourly` (module × severity × HTTP status class per hour) is maintained on write; KPIs and charts (`stats()`) read only that, the timeline falls back to raw rows for ranges ≤ 6 h. Full-text search is a contentless FTS5 table (`contentless_delete=1`, rows removed by trigger) with a `LIKE` fallback; `ftsQuery()` quotes every term so user input never becomes FTS syntax. Pagination is cursor-based (`before` = last id), never `OFFSET`. `redact()` masks payload keys ending in password/token/secret/hash/cookie/… (`tokenId`, `sha256` stay readable) and truncates; `diff(before, after)` produces the `changes` field for CRUD before/after states. Query strings and SQL parameters are never stored. `instrumentDatabase(db)` wraps the main `DatabaseSync` in a `Proxy` that times every statement: slow queries (`slowQueryMs`) → WARNING, errors → ERROR with stack, optional full tracing (`traceQueries`, DEBUG); the events DB itself is not instrumented (would recurse). `job(name, fn, { quiet })` wraps background jobs (start/end/duration/error, shared run id in `request_id`). Retention (`purge()`, hourly from `runMaintenance()`): days per severity (0 = never) and `maxRows` from the one-row `event_settings` table (editable at `/admin/logs/settings`), audit rows only by `auditDays` (= `AUDIT_LOG_RETENTION_DAYS`, env-only), optional gzip-NDJSON archive to `DATA_DIR/log-archive/` before deleting. `importLegacyAudit()` moves the rows of the old `audit_log` table (still the target of `lib/migrate-legacy.js`) into the event log once at `start()`. Everything in `record()` is try/catch'd — logging never fails the action; write failures go to the console at most once a minute
- **`lib/event-catalog.js`**: severities (`DEBUG 10` … `CRITICAL 50`), modules (`auth`, `users`, `files`, `tickets`, `mail`, `api`, `http`, `database`, `backup`, `jobs`, `security`, `system`) with German labels, and the mapping of audit event names to module/severity (`AUDIT_EVENTS`; unknown names are derived from prefix/suffix, so a new `auditLog.log()` call needs no entry unless the derivation is wrong), plus `moduleForPath()` for requests
- **`lib/audit-log.js`**: thin facade over the event log keeping the old interface — `auditLog.log(event, detail)` becomes an event with `audit = 1` (an `ip` in `detail` goes into the `ip` column), `read({ limit })` returns `{ id, ts, event, ip?, ...detail }` newest first as before (heartbeat, `/api/v1/audit-log`, the admin widget). Pass `detail.changes = diff(before, after)` for before/after states. A logging failure is swallowed — it must never fail the action it's logging
- **`lib/backup-store.js`**: automatic, schedulable backups of the SQLite database itself (not the ISO files in `uploads/`, which stay the admin's own filesystem/volume-backup responsibility). A backup is a consistent snapshot via SQLite's own `VACUUM INTO`, run synchronously on the same open `DatabaseSync` — deliberately not the newer `node:sqlite` `backup()` function, which would silently raise the project's declared Node floor (`>=22.5.0`, see `package.json`) past what that function actually requires. Written to `DATA_DIR/backups/` (rides along with the already-documented/mounted `DATA_DIR` volume, no new mount needed) as `iso-share-<timestamp>-<random suffix>.db` plus a `.sha256` sidecar — the random suffix exists only because `VACUUM INTO` refuses to overwrite an existing file, so a timestamp alone could collide within the same second (e.g. a double-clicked "Jetzt sichern"); the schedule (`interval_minutes`/`retention_count`/`enabled`) lives in the one-row `backup_settings` table, editable at runtime via `/admin/backup-settings` without a restart — `server.js` re-arms its `setInterval` (`armBackupTimer()`) right after a settings write. Regular backups beyond `retentionCount` are pruned oldest-first; a `pre-restore-` prefixed safety snapshot (taken automatically right before every restore) is deliberately exempt from that pruning, only removable explicitly. `restoreBackup()` is the one genuinely destructive operation: it verifies the target backup's checksum, takes that pre-restore safety snapshot of the *current* database while it's still open, then closes the `DatabaseSync` instance and copies the chosen backup file over the live one (clearing any now-orphaned `-wal`/`-shm` files). It does not attempt a live reopen — every other store in this file holds a fixed `db` reference from `createApp()`, so swapping the file under a running process without a restart would mean converting all of them to a getter, a much larger change for a rare, admin-initiated action. Instead `server.js`'s `POST /admin/backups/:filename/restore` handler responds to the request and then calls `process.exit(1)` on `res.on('finish', ...)`, relying on `docker-compose.yml`'s `restart: unless-stopped` (or an equivalent process supervisor) to bring the app back up against the now-restored file — the same "one re-login is an acceptable cost" tradeoff `lib/migrate-legacy.js` already accepts for sessions. The restore is recorded as `backup_restored` in the event log, which lives in `events.db` and therefore survives the swap; the marker file `DATA_DIR/last-restore.json` is still written for operators who script against it. A single `running` flag guards `createBackup()` and `restoreBackup()` against each other (restore holds it for its *entire* duration, not just the pre-restore snapshot, so two concurrent restores can't both reach `db.close()`); a collision throws with `code: 'backup_in_progress'`, surfaced by `server.js` as `409`. If the file copy itself fails *after* `db.close()` (disk full, permissions), the thrown error carries `dbClosed: true` — `server.js` treats that as fatal regardless of the underlying error and forces the `process.exit(1)` anyway, since a process that keeps running with a permanently closed `db` handle is worse than one that restarts against a possibly-still-old database (the pre-restore safety snapshot stays available either way)
- **`lib/ticket-store.js`**: support tickets in `tickets`/`ticket_messages`/`ticket_attachments`. Every ticket belongs to a customer account (`customer_id`, see `lib/customer-store.js`); `requester_email`/`requester_name` are a snapshot for mails and for tickets without an account (imported from the old guest-ticket prototype by `migratePrototypeTickets()` in `lib/db.js`, claimed automatically by `claimTicketsByEmail()` once someone registers and verifies that exact address). Public sequential `number` (#1001, ...) for URLs and mail subjects, assigned via `MAX(number)+1` (race-free because `DatabaseSync` is synchronous). Helpdesk status machine: `new` (no support reply yet) -> `pending` (support replied, waiting on customer) <-> `open` (customer replied) -> `resolved` (customer can reopen by replying) -> `closed` (final, replies rejected). Messages have `kind` `reply`/`note`/`event` plus an `internal` flag: notes and internal events (priority/category changes, ratings) are never shown to customers (`listMessages({ includeInternal: false })`). Only "notable" transitions (to/from resolved/closed) create a timeline event; the routine `new/open -> pending` via a reply doesn't. Saved views (`ADMIN_VIEWS`/`CUSTOMER_VIEWS`) are fixed SQL fragments looked up by name; `listTickets()` is paginated and searches number/subject/requester/tags/message bodies (customers never match internal notes). Also unread flags per side, first-response/resolution timestamps and `stats()` for the admin KPIs, CSAT `rate()` (once, only resolved/closed), and the automation queries used by `lib/ticket-automation.js`. `createTicket({ author: 'admin' })` is a ticket the support opens for a customer (first message is the support's, status `statusAfter` — never `new` —, `first_response_at` set immediately); `source` (`web`/`email`/`admin`) records the channel. `iso_file` is a *name snapshot* of the ISO a ticket is about (no FK — the file may be deleted/replaced later), set via `setIsoFile()`; `setTags()`/`setIsoFile()` add internal timeline events like priority/category do. `mergeTickets(source, target)` (same customer only, target not closed) moves messages and attachments into the target in one transaction, closes the source with `merged_into_id` — both detail routes 301 the old number to the target, and `mail-inbound.js` follows `merged_into_id` for replies to the old thread. `splitTicket(source, { messageIds, subject, … })` is the counterpart: selected replies/notes (never events; at least one reply must stay) move with their attachments into a new ticket of the same customer whose `created_at`/status derive from the moved messages (`split_from_id` links it back, shown in both sidebars via `listSplitChildren()`); the source's status is left alone, only its activity timestamps are recomputed so the SLA doesn't hang on a moved message; both threads get a public cross-reference event. **SLA**: `SLA_DUE_SQL` is a parameter-free SQL expression (so it fits the fixed `ADMIN_VIEWS`/`SORTS` fragments, "now" via `julianday()`): the next support reply is due `first_response_minutes` after `created_at` for `new`, `next_response_minutes` after the last customer message for `open`; `pending`/`resolved`/`closed` have no deadline, so the clock pauses automatically while the customer is on the move. Every ticket row carries `slaDueAt`/`slaMinutes`; view `overdue`, sort `due`; `sla_notified_at` (reset by every reply and status change) makes the breach mail fire once per deadline. **Snooze** (Wiedervorlage): `snoozed_until` (migration 5) is admin-only state, not a status — `snooze()`/`unsnooze()`, only for active, non-merged tickets. `AWAKE_SQL`/`SNOOZED_SQL` compare against SQL "now", so a ticket drops out of `active`/`new`/`open`/`pending`/`urgent`/`unread` into view `snoozed` (sort `snooze`) and reappears the moment the time passes, no job needed; `overdue` deliberately ignores snooze (the SLA keeps running — it's a promise to the customer). A customer reply and resolved/closed (`statusFields()`) clear it, a support reply doesn't; reminder/auto-resolve skip snoozed tickets. Preset times ("Morgen 9:00" etc.) are wall time in `APP_TIMEZONE`, computed in `lib/snooze.js`; never shown to the customer nor part of `exportForCustomer()`
- **`lib/customer-store.js`**: customer accounts (`customers`, `customer_tokens`), completely separate from the one admin account. Emails stored lowercase (one account per mailbox), passwords `scrypt` like `lib/password-store.js`; `authenticate()` always runs exactly one scrypt round (dummy hash for unknown addresses) so timing doesn't reveal whether an account exists. One-time tokens (`verify` 24h, `reset` 1h, `email_change` 24h with the new address as `payload`) are stored as `sha256` only; `issueToken()` invalidates older tokens of the same purpose, `consumeToken()` deletes on use. `notify` holds the opt-outs (`replies`/`status`/`reminders`); security mails ignore them
- **`lib/ticket-config-store.js`**: runtime ticket configuration editable at `/admin/ticket-settings` without a restart: categories, canned responses, the automation deadlines (`ticket_settings`, one row), the SLA response deadlines per priority (`ticket_sla`, hours in the UI, minutes in the table, 0 = none; rows are `INSERT OR IGNORE`-seeded on every construction because the deadline is computed in SQL, where JS defaults would be invisible) and the reply greeting/signature (`ticket_reply_template`, one row — its own table so existing databases need no `ALTER TABLE`; defaults apply until the first save). `seedDefaults()` creates a few default categories only on the very first start (the settings row is the "already seeded" marker, so a deliberately emptied category list stays empty)
- **`lib/reply-template.js`**: pure functions for the salutation (`Hallo {name},`) and closing (`Mit freundlichen Grüßen\n{agent}\nISO Share Support`) of admin replies. `buildReplyDraft()` pre-fills them *into* the composer's textarea (greeting, blank line, caret position, blank line, closing), so the admin sees and freely edits the exact text that goes out — the server adds nothing on save; `isOnlyTemplate()` only rejects a submit that is still just the untouched pre-fill. `{name}` is the customer's current account name (fallback: the ticket's requester snapshot), `{agent}` the configured display name (fallback: the admin username via `ctx.adminUsername()`); an empty placeholder is dropped cleanly (`Hallo,` rather than `Hallo ,`). `composer.js` puts the caret between greeting and closing on first focus (`data-reply-caret`), clears the untouched pre-fill when switching to an internal note and restores it when switching back; the textarea has a literal newline right after its opening tag because HTML swallows exactly one leading newline (matters when the greeting is empty). `ticket-mail.js` drops its own `Hallo …` intro when the reply already starts with a salutation
- **`lib/attachment-store.js`**: ticket attachments. Metadata in `ticket_attachments`, bytes under `DATA_DIR/ticket-attachments/<uuid>` (never served statically; not part of the DB backups, but in the same volume). The type comes from magic bytes only (PNG/JPEG/GIF/WebP/PDF/ZIP/GZIP, plus UTF-8 text for a small set of extensions): no SVG/HTML, the client's `Content-Type`/extension never counts. Two-step `inspect*()` then `storeAll()`, so a rejected file never leaves a half-created message. Limits via `TICKET_ATTACHMENT_MAX_MB` (default 10) and 5 files per message. Writing goes through `commit(items, write)`: the files are staged under a fresh UUID first, then `write()` (e.g. `() => ticketStore.createTicket(...)`) and the attachment rows run in *one* transaction (`lib/db-tx.js`), so a failure never leaves a ticket without its attachments (or, on retry, a duplicate ticket) nor a row without a file; staged files are removed on failure, and `sweepOrphans()` (hourly from `runMaintenance()`) deletes files older than an hour that have no row. `commit()` also checks the `MIN_FREE_DISK_MB` reserve (`hasSpaceFor()`, same `diskInfo` as `lib/chunked-upload.js`) and throws `AttachmentError` `insufficient_storage`; `attachmentsMiddleware()` in `lib/routes/helpers.js` runs the same check against `Content-Length` *before* multer writes anything to `tmp-uploads/`. Every call site uses `commit()` — `storeAll()` only remains for attaching to an existing message
- **`lib/mail-outbox.js`**: every outgoing mail goes into `mail_outbox` first and is sent asynchronously by a small worker (request handlers never wait on SMTP, nothing is lost on restart). Failed sends are classified by `classifyError()`: a 5xx (no such mailbox, rejected as spam) ends as `failed` immediately; a 4xx for one recipient (e.g. GMX's `450 … Try again later` throttling after a burst to one mailbox) retries with backoff (1 min up to 6 h) and defers the other due mails to that address without spending their attempts; a connection/auth/421 error pauses the whole queue instead of every mail burning its own attempt. `sendIntervalMs` (2 s in production, 0 with an injected test transport) spaces consecutive sends so a burst doesn't look like a spam wave. Retried mails end as `failed` after `MAX_ATTEMPTS`, visible and retryable at `/admin/ticket-settings`; sent mails are pruned after 30 days. With mail disabled, `enqueue()` stores nothing. Attachments: only ticket-attachment *ids* are stored (`attachments_json`), resolved to file paths by the injected `resolveAttachments()` at send time; an attachment deleted meanwhile is simply missing from the mail
- **`lib/mail-templates.js`** / **`lib/ticket-mail.js`**: `compose()` builds both the text and the HTML part from one structure. The HTML mirrors the app's design (card, status pill, message bubble with avatar, primary button) using the `tokens.css` colors converted to hex (`LIGHT`/`DARK` — mail clients support neither `oklch()` nor CSS variables); light is inline, dark mode comes via `@media (prefers-color-scheme: dark)` with `!important` class overrides. All user input is escaped, layout is tables + inline styles for client compatibility, plus a hidden preheader and a per-recipient footer with links. Outlook for Windows (Word engine) is the lowest common denominator: spacing/backgrounds/borders only on `<td>` (plus `bgcolor`), never on `div`/`span`/`a`; fixed 580px width via an MSO ghost table (Word ignores `max-width`); line breaks as `<br>` (no `white-space:pre-wrap`); px line-heights with `mso-line-height-rule:exactly`; circles (logo, avatar) and the button as VML inside `<!--[if mso]>` with the normal HTML in `<!--[if !mso]><!-->`; an MSO font override so Word doesn't fall back to Times New Roman; the dark rules are repeated under `[data-ogsc]`/`[data-ogsb]` for Outlook.com/the Outlook apps, which ignore `prefers-color-scheme`. Only the big card's rounded corners stay square in Outlook for Windows; SMTP and IMAP connections require TLS ≥ 1.2 with a valid certificate; `stripQuotedReply()` cuts quoted history from inbound replies. `ticket-mail.js` holds every mail occasion (verify, account exists, reset, password changed, email change, account deleted, ticket created, support reply, status change, reminder, reply-to-closed rejection, admin notifications, test mail). Threading: each ticket mail gets its own `Message-ID` plus `In-Reply-To`/`References` pointing at a per-ticket root id that carries an HMAC over the ticket id (`threadSecret` derived from the session secret); `ticketIdFromReferences()` only accepts a validly signed reference. All links are built from `PUBLIC_URL`, never from the request's `Host` header (password-reset poisoning). Ticket attachments go along as real mail attachments in order until `MAIL_ATTACHMENT_MAX_MB` (`attachmentMaxBytes`) is used up, the rest is listed as "… (im Portal)"; the customer's own confirmation mail never sends their files back. Further occasions: `ticketOpenedBySupport()`, `ticketMerged()`, `slaBreached()` (admin)
- **`lib/mail-inbound.js`** / **`lib/imap-poller.js`**: customers can answer by email. `imap-poller.js` uses `imapflow` (third deliberate dependency exception: hand-written MIME decoding would be far riskier), polls every `IMAP_POLL_SECONDS` and tracks progress by **UID**, not `\Seen` (`imap_state` via `lib/inbound-mail-store.js`: `UIDVALIDITY` + last UID, searches `last+1:*` and filters the RFC quirk that `n:*` always returns the highest UID) — so a human reading the mailbox in a mail client no longer makes mails invisible; only the very first run (or a changed `UIDVALIDITY`) falls back to "unseen" so old read mail doesn't turn into tickets. It still marks each mail seen after processing (also on failure, so one broken mail can't block the queue) and, with `IMAP_PROCESSED_MAILBOX`, moves it there (created once if missing; failure only logs). Per mail it downloads at most `maxAttachmentFiles` attachments, each capped at `maxAttachmentBytes` (`streamToBuffer()` enforces it even if the server ignores `maxBytes`); one that BODYSTRUCTURE already reports as too large is passed as `{ tooLarge: true }` without downloading, and `attachmentCount` carries the real total. `isAutoSubmitted()` also treats `List-Id`/`List-Unsubscribe`, an empty `Return-Path` and `mailer-daemon`/`postmaster` senders as automatic and hands a decoded object to `mail-inbound.js`, which is testable without a mail server. A mail is added only if it isn't auto-submitted, carries a validly signed thread reference (the `[#1042]` subject alone never counts, it's trivially forgeable), comes from exactly the ticket account's address, the account isn't disabled and the ticket isn't closed (then the customer gets a short "please open a new ticket" mail). Everything else is dropped silently (audit log only, no backscatter). Invalid attachments are skipped individually with a note in the message. **New tickets by mail** (no signed reference at all) only when `IMAP_AUTHSERV_ID` is set, the sender has a verified, non-disabled account, `lib/mail-auth.js` confirms DKIM/DMARC, and the account opened fewer than 5 mail tickets in the last hour (loop guard); the subject loses `Re:/AW:/Fwd:/WG:` prefixes. A signed reference to a *deleted* ticket never turns into a new ticket. With `IMAP_AUTHSERV_ID` set, *replies* also need DKIM/DMARC (the signed reference alone is known to anyone a ticket mail was forwarded/CC'd to). Every mail is processed at most once (`inboundStore.claim()` on sender + Message-ID, fallback `dedupKey` from the poller), the "ticket is closed" notice goes out at most once per ticket per 24 h (`notifyOnce()`) and never to a mail with `suppressAutoResponse` (`X-Auto-Response-Suppress`, `X-Loop`, Exchange rule loop) — otherwise it ping-pongs with autoresponders that don't set `Auto-Submitted`. Attachments go through `attachmentStore.commit()`; if they can't be stored (disk full), the message is kept without them plus a note. `stats()` counts results for `/metrics` (`iso_share_mail_inbound_total{result}`)
- **`lib/ticket-automation.js`**: runs every 10 min from `server.js`: reminder after `pendingReminderDays` without customer reply, auto-`resolved` `pendingAutoResolveDays` after the reminder, auto-`closed` `autoCloseDays` after resolving. `reminder_sent_at` is set even if the customer opted out of reminders (otherwise auto-resolve would never trigger for them); any customer reply resets it, and so does every new support reply (a fresh answer restarts the waiting period instead of being auto-resolved right away because an older reminder is already past due). Also sends the one-time SLA breach mail to `TICKET_NOTIFY_EMAIL` (`dueForSlaBreach()`/`markSlaNotified()`), and tidies up due snoozes (`dueForWake()` → `unsnooze({ reason: 'due' })`: clears the column, marks the ticket unread, internal "Wiedervorlage fällig" event)
- **`lib/mail-auth.js`**: `authenticatedSender(authResults, { authservId, fromAddress })` — decides from the `Authentication-Results` header (RFC 8601) whether a new mail really comes from its sender's domain. Only the **topmost** header whose authserv-id equals `IMAP_AUTHSERV_ID` counts (anyone can add more of these headers; only the own server's is trustworthy, and it sits on top). Accepts `dmarc=pass` with `header.from` = sender domain, or `dkim=pass` whose `header.d` is the sender domain or a parent of it (never a bare TLD); SPF alone never counts (envelope sender only). `headerValues()` keeps repeated headers in order — `imap-poller.js`'s `parseHeaders()` keeps only the last (= the forgeable) one. Pure, testable without a mail server
- **`lib/markdown.js`**: dependency-free Markdown subset for knowledge-base articles (`#`–`###` → h2–h4, lists, fenced code, bold/italic/inline code, links, bare https URLs). Everything is escaped **first**, tags are produced afterwards, so raw HTML stays visible text; links only to `http(s):`, `mailto:` and `/…` paths (no `//host`, no backslash — browsers read `/\host` as protocol-relative); external links get `rel="noopener noreferrer"`. `plainExcerpt()` for lists and suggestions
- **`lib/kb-store.js`**: knowledge-base articles (`kb_articles`): slug derived once from the title and then stable (renaming the title must not break links already sent in replies/mails; the admin can change it explicitly), `LIKE` search (fine for a handful of articles, no FTS), `suggest()` for the ticket form (any word matches, title hits weigh double, published only), anonymous `views` counter for the report page
- **`lib/ticket-reports.js`**: pure SQL behind `/admin/reports`: created/resolved counts, median/average first-response and resolution time, SLA hit rate of first responses against the **current** deadlines (stated on the page), CSAT average/distribution/comments, distributions by category/priority/channel/ISO file, top KB articles. Support-created tickets are excluded from first-response/SLA. Buckets are days up to 45 days, else calendar weeks starting Monday 00:00 in `APP_TIMEZONE` (`clock.floorLocal`/`parseLocal`, DST-safe); `seriesGeometry()` precomputes the grouped-bar SVG like the event log's `timelineGeometry()`
- **`lib/routes/event-log.js`**: the event-log dashboard (`/admin/logs*`, all `checkAuth`-gated). Every filter (severity, module, range preset or custom `from`/`to` as wall time in `APP_TIMEZONE`, `q`, `audit`, `req`, `ip`, `event`, cursor `before`) lives in the GET query — shareable, works without JS, and `live-regions.js` can re-fetch the same URL. `parseFilters()`/`filterQuery()` round-trip it; `timelineGeometry()` precomputes the stacked-bar SVG. CSV export is `;`-separated with BOM and prefixes cells starting with `= + - @` with `'` (CSV injection); JSON export streams an array; both honor backpressure and log `events_exported`
- **`lib/routes/`**: the ticket system's routes live here instead of `server.js` (they alone would outgrow the rest of the file). `account.js` (`createCustomerAuth()` provides `loadCustomer`, hooked in by `server.js` right after the CSRF middleware so every page knows the customer, and `checkCustomer`; plus registration/verify/login/reset/settings/export/delete), `tickets-customer.js` (`/support`, `/account/tickets*`, `/attachments/:id`), `tickets-admin.js` (`/admin/tickets*` incl. `/new` and `/:number/merge`, `/admin/customers*`, `/admin/ticket-settings*` incl. `/sla`, `/admin/mail/*`), `kb.js` (`/support`, `/support/articles*`, `/admin/kb*`), `reports.js` (`/admin/reports`), `helpers.js` (multer error to form message, `formatMessage()` escape-then-linkify, relative times, `safeNextPath()` against open redirects). `server.js` builds one context object and calls the three `register*` functions
- **`lib/mailer.js`**: thin `nodemailer` (SMTP) wrapper; `nodemailer` is a deliberate dependency exception (after `@simplewebauthn/server`) because SMTP is easy to get subtly wrong by hand. Unlike most stores it throws on failure, because `lib/mail-outbox.js` needs the error for retries; "never fail the actual action" is guaranteed by the outbox, not here. Without `SMTP_HOST` (and without an injected test `transport`) mail is disabled (`enabled: false`) and the app keeps working; new customer accounts are then activated manually at `/admin/customers/:id`
- **`lib/migrate-legacy.js`**: one-time import of the pre-SQLite JSON state (file sidecars, `admin-password.json`, `admin-username.json`, `webauthn.json`, `totp.json`, `audit.log`, and any in-flight chunked-upload sessions under `tmp-uploads/`) into the database, run from `start()` before anything else. Each piece only imports into an *empty* table, so a second start never double-imports. After a successful import, the source file is deleted (and `uploads/.meta/` removed once empty) — the database is meant to be the sole, lasting home for this data, not a copy that drifts from a JSON file left sitting next to it. Sessions (express-session) are deliberately not migrated: they're ephemeral, so one re-login after the upgrade is an acceptable cost, and `data/sessions/` (if left over from before this change) is never touched
- **`lib/zip-stream.js`**: hand-rolled streaming ZIP writer (`writeZip()`) for the bulk-download route, store method only (no compression — ISOs barely compress anyway) with a data descriptor per entry, so it never needs to know a file's CRC32/size before streaming it straight from disk into the response. Deliberately no Zip64: `fitsInClassicZip()` lets `server.js` reject a selection whose per-file or total size would overflow the classic 32-bit fields *before* the stream starts, rather than emit a truncated/corrupt archive
- **`lib/config-check.js`**: validates the deployment config inside `createApp()` *before* the database is opened. In production (`isProd`) a missing `TRUST_PROXY` (Node doesn't terminate TLS, so without `trust proxy` the `secure` session cookie is silently never set), a missing/non-https/localhost `PUBLIC_URL` while SMTP is enabled, or invalid size limits throw `code: 'invalid_config'` with *all* problems at once — the process refuses to start rather than run half-broken. Outside production the prod-only findings are warnings, so local development needs no proxy. A missing `METRICS_TOKEN` in production is only a warning
- **`lib/time.js`**: `createClock(APP_TIMEZONE)` (default `Europe/Berlin`) — the **only** place that turns a timestamp into wall-clock time and back. Storage stays UTC everywhere (epoch ms: unambiguous across DST, retention periods stay plain subtraction); only *display* uses the zone. `server.js` exposes `formatDate`/`formatDateTime`/`formatTime`/`formatStamp`/`zoneName`/`appTimeZone` as `app.locals`, so views never format dates themselves (no `toLocaleTimeString()` in a view — it would use the server's zone, which is UTC in the container). Browser scripts read the zone from `<meta name="app-time-zone">` (`head.ejs`) instead of using the browser's own, so server-rendered and live-updated entries agree. `parseLocal()` reads a `datetime-local` value as wall time (ambiguous October hour → the earlier one, the missing March hour → shifted forward), `floorLocal()` aligns chart buckets to local midnight/hours across DST, `formatIsoLocal()` gives ISO 8601 with offset. Machine-readable output stays UTC ISO: `/api/v1`, data exports, backup/archive file names, JSON console logs; the event-log CSV/JSON export carries both (`time_utc` + `time_local`). ZIP entries get their DOS timestamps from `clock.parts` (DOS time has no zone, extractors read it as local). An unknown zone name throws `code: 'invalid_config'` in `createApp()`. Node ships the tz data via ICU — no `tzdata` package in the image
- **`lib/logger.js`**: dependency-free logger with the `console` interface (`log`/`info`/`warn`/`error`/`debug`/`critical`), so every module that takes `log = console` accepts it unchanged. **Two destinations:** the console stays quiet on purpose — the root logger prints from `LOG_LEVEL` (startup, shutdown, config warnings), module loggers from `log.child('mail')` etc. only from `detailLevel` (`LOG_CONSOLE_LEVEL`, default `warn`); the sink (`attachSink(events.fromLog)`, the event log) gets *every* message regardless of level, with the child's module. Messages before the sink is attached (config check) are buffered. `child(module, { sink: false })` is console-only for lines that already are their own event (request lines, unhandled errors). `childLog(log, module)` also works with plain `console`-like test loggers. `LOG_FORMAT=json` (default in production) writes one JSON line per entry, `pretty` readable lines. `requestLogger()` is the first middleware in `server.js`: it assigns `req.id` (a valid incoming `X-Request-Id` or a fresh UUID), echoes it as `X-Request-Id`, calls `onFinish` (→ `events.recordRequest`) and writes the console line at `info` (so: hidden by default), only 5xx as `error`. It never logs the query string — one-time tokens live there (`/account/verify?token=…`) — and skips `/healthz`, `/metrics` and static assets. Tests pass a silent logger or `requestLog: false`. When adding logging to a module: pass it `childLog(log, '<module>')` in `server.js` and log details at `info`/`debug` with an `event` field (`log.info('…', { event: 'x_done', … })`) — they land in the event log, not the console
- **`lib/lifecycle.js`**: `createShutdown()` for SIGTERM/SIGINT: stop accepting connections, close idle keep-alives, let in-flight requests finish for up to `SHUTDOWN_TIMEOUT_MS` (default 30 s, must stay below `stop_grace_period` in `docker-compose.yml`), then force-close the rest, run `instance.stop()` (timers, outbox, DB close) and exit — idempotent, with a hard exit after timeout + 5 s. `installProcessHandlers()` also routes `unhandledRejection`/`uncaughtException` into the same orderly shutdown with exit code 1, relying on the restart policy. Only wired up in the `require.main === module` block, never in tests' `createApp()`
- **`lib/retention.js`**: GDPR storage limitation, run at `start()` and hourly (`maintenanceIntervalMs`, 0 disables): deletes never-verified customer accounts older than `UNVERIFIED_ACCOUNT_RETENTION_DAYS` (default 30, silently — no "account deleted" mail to an address that was never proven to belong to the registrant) and `closed` (not `resolved`) tickets whose `closed_at` is older than `CLOSED_TICKET_RETENTION_DAYS` (default 0 = off, the right period depends on the operator's obligations). Deletion goes through the same store functions as the admin actions (attachment files, sessions, outbox copies included). Logs `retention_purge` when anything was removed. Audit rows are no longer deleted here but by the event log's own `purge()` (`AUDIT_LOG_RETENTION_DAYS` is passed through as `auditDays`). `app.locals.retentionPolicy` and `app.locals.eventRetention()` (the event log's current per-severity periods) feed `views/privacy.ejs`, so the privacy policy always states the periods actually in effect — keep it that way when adding a new retention rule
- **Express-based**: Uses Express.js with EJS templating for server-side rendering
- **Session-based auth**: Simple password authentication with express-session, session state persisted via `SqliteSessionStore` (see above)
- **File management**: multipart upload (`/upload`, no-JS fallback) and a resumable chunked-upload protocol (`/upload/init` + friends, what `upload.js` actually uses) both land in `uploads/` through `lib/move-file.js`
- **Two-tier access**: Public file listing/download and admin upload/delete functionality
- **Frontend**: No CSS/JS framework and no CDN — everything is served from `public/`. Views reference every script/stylesheet through `asset('/js/x.js')` (`app.locals.asset` in `server.js`), which appends `?v=<content hash>` computed once at startup — `express.static` caches for 1h, and without the version a browser would keep running an old script against new HTML after an update. Add new `<script>`/`<link>` tags the same way. `public/css/tokens.css` holds the design tokens (dark is the default, `[data-theme="light"]` overrides), `public/css/main.css` the components. The scripts in `public/js/` are small self-contained IIFEs wired up declaratively via `data-*` attributes, so a view opts into behaviour by adding markup, not by adding a script tag. `views/partials/file-row.ejs` renders one file's row + its collapsible detail row (checksum, verify snippet, boot info) and is shared by `index.ejs` and `admin.ejs`
- **Live updates**: nothing on a page should need a manual reload to show new data. `public/js/heartbeat.js` covers `index.ejs`/`admin.ejs` via `/partials/listing` resp. `/admin/partials/listing` (file rows with their own diff logic, plus a `regions` map for the simple areas: nav ticket counter, ticket tab badge/overview, backups + schedule, the upload form's "replaces" select; on admin.ejs also `account: { username, totpEnabled }` as plain values, since those fields belong to `account-forms.js`/`totp.js`). Table, search and the "no files" hint are always in the markup and toggled via `[data-files-present]`/`[data-files-empty]` — never wrap them in `<% if (files.length) %>`, or the first file can't appear live. Every other page opts into `public/js/live-regions.js` with `<body data-live-page [data-live-url]>`: it re-fetches the same page every 20s (`X-Idle-Background: 1`, so the admin idle timeout isn't extended) and swaps each `[data-live-region="key"]` whose server markup changed — no second template, no extra endpoint. A region is never swapped while the user works in it (focused field, dirty field/checkbox/select, open `<dialog>`, or with `data-live-guard-hover` while hovered); `[data-live-key]` marks items so new ones flash and open `<details>` stay open. `data-live-url` is needed wherever the view is also rendered from a POST error path (the poll must hit the GET URL). `live-regions.js` must be included *before* the other scripts, since it snapshots each region's pristine markup. When adding dynamic data to a page, wrap it in a region (or add it to the heartbeat's `regions` on admin.ejs). A region must exist even while its content is empty (a conditional card goes *inside* the region — `.live-slot` is a `display: contents` wrapper for flex/stack layouts), and an unselected `<select>` counts as pristine (the dirty check compares against the browser's default option, not just `defaultSelected`). Pages without `data-live-page` that still show the nav (imprint, KB editor, event detail, notice) include `live-regions.js` anyway: it then only polls `GET /partials/nav` for the ticket counter. A page GET with side effects must skip them for `X-Idle-Background: 1` (e.g. the KB article view counter). The shared `pollLimiter` (60/min) is keyed per logged-in session, per IP only for anonymous clients
- **Confirmations and scroll position** (both loaded on every page via `partials/footer.ejs`): every confirmation goes through the one custom modal in `public/js/confirm.js` — never `window.confirm()`/`alert()`. Declarative: `data-confirm="Text"` on a submit button, an `<option>` (only when newly chosen, not the preselected one) or the `<form>`, plus `data-confirm-title`/`-ok`/`-variant="primary"` and `data-confirm-type` (value to type into the modal; `{field}` placeholders pull a form field's displayed value). JS code uses `window.appConfirm({...})` → `Promise<boolean>` / `window.appAlert()`. The no-JS safeguard stays in the form wrapped in `[data-confirm-inline]` (required checkbox / type-to-confirm field, still checked server-side); `html.js` (set by `theme-init.js`) hides it via CSS, and confirm.js drops its `required` at click time and fills it after confirmation — it deliberately doesn't touch the DOM on load, since `live-regions.js` snapshots region markup. Admin-page dialogs that predate this (`admin.ejs` backups, tokens, passkeys, file delete) keep their own `<dialog>`s. `public/js/scroll-keep.js` stops the jump to the top after a classic POST+redirect: on submit it stores scrollY plus the submitted form's `action` and viewport offset, and after a reload *on the same path* puts that form back at the same screen position (falls back to scrollY if the form is gone), strips the action's `#anchor`, and re-shows an out-of-view `.alert--success` as a toast. It skips other paths, server-set anchors (reply → `#message-…`), `fetch`-sent forms and `[data-scroll-top]`; scripts that navigate themselves call `window.keepScroll()` first. Scrolling uses `behavior: "instant"` because `main.css` sets `scroll-behavior: smooth`
- **Progressive enhancement is load-bearing**: the newer platform features (cross-document view transitions, `@starting-style`, scroll-driven `.reveal` animations, Popover API + anchor positioning) are all layered so an unsupporting browser gets the static version instead of a broken one. Two guards must stay: the `.reveal` rules live inside `@supports (animation-timeline: view())` because their `opacity: 0` start frame would otherwise hide the cards permanently, and `@supports not selector(:popover-open)` hides the theme menu so it can't sit invisible over the nav (`theme.js` then falls back to cycling on click). The detail row starts `[hidden]` server-side and only opens via `row-details.js`, so a no-JS client still gets the checksum through `/checksums`

### File Operations
- Files are stored in the `uploads/` directory; per-file metadata (checksum, ISO info, download count) lives in the `files` table of the SQLite database at `data/iso-share.db` (see `lib/db.js`)
- Only `.iso` files are accepted for upload
- **Bootstrap-once env vars** — `ADMIN_PASSWORD`, `ADMIN_USERNAME`, `SESSION_SECRET`: each is read only until its row in the database exists, which `start()` guarantees happens on the very first run (generating a value where there's no sane default, namely the password and the session secret). After that the DB row is what counts, permanently — changing or removing the env var later does nothing, the same as an explicit change via `/admin-password`/`/admin-username` would. This is deliberate: a secret that lives forever in an env var (`.env`, `docker-compose.yml`, shell history, `docker inspect`) is worse operational practice than one written once to the app's own database. To force a fresh bootstrap from the env var again, delete the corresponding row (or all of `data/iso-share.db`) — see "Inspecting the database" below for how
- `MAX_FILE_SIZE_MB` (default 8192) caps both the multipart and the chunked-upload path — a plain runtime cap, not a secret, so it stays an env var read fresh on every start; there's no admin-UI route to change it, unlike password/username
- `SMTP_HOST`/`SMTP_SECURE` (default `true` = SMTPS, implicit TLS; `false` = STARTTLS with `requireTLS`, never plaintext)/`SMTP_PORT` (default 465 resp. 587)/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`, `TICKET_NOTIFY_EMAIL` (admin notifications), `IMAP_HOST`/`IMAP_SECURE` (default `true` = IMAPS; `false` = forced STARTTLS)/`IMAP_PORT` (default 993 resp. 143)/`IMAP_USER`/`IMAP_PASS`/`IMAP_MAILBOX` (INBOX)/`IMAP_POLL_SECONDS` (60)/`IMAP_PROCESSED_MAILBOX` (empty = leave processed mails in the mailbox), `SUPPORT_REPLY_TO` (Reply-To of ticket mails, defaults to `IMAP_USER` if that is an address), `PUBLIC_URL` (base for every link in mails; required in production, deliberately never derived from the `Host` header) , `TICKET_ATTACHMENT_MAX_MB` (10), `MAIL_ATTACHMENT_MAX_MB` (10, sum of real attachments per ticket mail, 0 = names only) and `IMAP_AUTHSERV_ID` (authserv-id of the own mail server; enables new tickets by mail, see `lib/mail-auth.js` and `OPERATIONS.md`). All env-only like `TRUST_PROXY`/`DATA_DIR`: credentials and public URLs are deployment decisions, not runtime settings. Without `SMTP_HOST`/`IMAP_HOST` the respective direction is simply off
- `DATA_DIR` (default `data/`) is where the SQLite database (`iso-share.db`, plus its `-wal`/`-shm` files) and the event log (`events.db`, `log-archive/`) live — sessions, file metadata, passkeys, admin password/username, the session secret, TOTP and the audit log all live in it. Also holds `backups/` (see `lib/backup-store.js`) and, after a restore, `last-restore.json`. Mount this as a volume in Docker, not `/tmp`. This one **can't** move into the database itself for the obvious circular reason (it says where the database is)
- Operational env vars (all env-only, read fresh on every start): `MIN_FREE_DISK_MB` (default 1024, reserve that must stay free after all running uploads, see `lib/chunked-upload.js`), `METRICS_TOKEN`, `APP_TIMEZONE` (`lib/time.js`), `LOG_FORMAT`/`LOG_LEVEL`/`LOG_CONSOLE_LEVEL` (`lib/logger.js`), `SHUTDOWN_TIMEOUT_MS` (`lib/lifecycle.js`), `AUDIT_LOG_RETENTION_DAYS`/`UNVERIFIED_ACCOUNT_RETENTION_DAYS`/`CLOSED_TICKET_RETENTION_DAYS` (`lib/retention.js`). Numeric ones go through `envNumber()` in `server.js`, which — unlike `Number(x) || default` — keeps an explicit `0` ("off"). `.env.example` lists every variable; deployment, backups and monitoring are documented in `OPERATIONS.md`
- `TRUST_PROXY` and `NODE_ENV` also stay env-only, but for a different reason than `DATA_DIR`: they're trust decisions about the deployment environment itself (is there a real reverse proxy overwriting `X-Forwarded-For`? is this production?), which have to be fixed *before* any request — let alone any database row an admin could edit through the UI — is allowed to influence how the server interprets one. Making either one DB-editable from inside the app would let a web-reachable setting flip a trust boundary that's supposed to be decided by whoever controls the deployment, not by the app itself

### Inspecting the database
There's no separate DB server to connect to — `data/iso-share.db` is a plain SQLite file, safely readable while the app is running (WAL mode, see `lib/db.js`):
```bash
node -e "
const { DatabaseSync } = require('node:sqlite');
const db = new DatabaseSync('./data/iso-share.db', { readOnly: true });
console.log(db.prepare('SELECT name, downloads, sha256 FROM files').all());
db.close();
"
```
For point-and-click browsing, "DB Browser for SQLite" (free, cross-platform) or a `.db`-viewer extension for the editor works too — open read-only while the server is running. Table names match the schema in `lib/db.js`. Writing to the DB by hand while the server runs is best avoided (go through the app's routes instead, so things like auto-tags/checksums stay consistent) — reading is always safe.

## Key Routes Structure

- `/` - Public file listing with search and download
- `/checksums` - `SHA256SUMS` (coreutils format) for every file with a current checksum
- `/api/files.json` - JSON equivalent of the file listing (same fields as the index page/`describe()`, honors `?q=` like `/search`), for scripts/CI/monitoring; public like `/checksums`, since it exposes nothing the listing doesn't already show

- `/partials/listing`, `/admin/partials/listing`, `/partials/nav` - heartbeat/live-update fragments (see "Live updates" above); `/partials/nav` returns only the nav ticket counter for the current admin/customer (empty for anonymous)
- `/healthz` - liveness endpoint for the Docker healthcheck; deliberately not `/`, which would render the whole listing every 30s. Runs a real `SELECT 1` and answers `503` if the database is unusable (e.g. after a failed restore)
- `/metrics` - Prometheus text-format counters (file count, storage bytes, downloads; uploads/deletes/login counters derived from the audit log, so they're only as complete as that log's trim window). Also operational gauges meant for alerting (`iso_share_mail_outbox{status}`, `iso_share_imap_last_poll_ok`, `iso_share_backup_last_timestamp_seconds`, `iso_share_disk_free_bytes{volume}`, `iso_share_hash_queue_pending`, `iso_share_upload_sessions`, `iso_share_db_bytes`, `iso_share_build_info{version,schema,node}`); example alert rules are in `OPERATIONS.md`. Public by default like `/healthz`, but since the operational values reveal more than the listing, setting `METRICS_TOKEN` requires `Authorization: Bearer <token>` (compared via SHA-256 + `timingSafeEqual`, 401 otherwise)
- `/files/:name/tags/:tag` (`DELETE`) - Admin-only removal of a single tag from a file (see `lib/metadata.js`). There is no route to add one: tags are assigned exclusively by `lib/hash-queue.js`/`lib/auto-tags.js` from the ISO itself (bootability, volume label) as part of the background hash run. Removing is JS-only via `public/js/tags.js`, the same precedent as `/webauthn/credentials/:id` and `/delete-bulk`; if the removed tag was an auto-tag it's recorded in `removedAutoTags` so the next rescan doesn't reattach it. `/` and `/admin-upload` also show a tag-filter bar (`views/partials/tag-filter.ejs`, driven by `listAllTags()` in `server.js`) listing every tag in use, and the search box grows a reset link back to the unfiltered listing whenever a query is active
- `/login` - Admin authentication (password, plus an optional passkey via `/webauthn/login/options` + `/webauthn/login/verify`, same rate limiters as the password form). A password login with TOTP enabled redirects to `/login/totp` instead of setting up the session directly
- `/login/totp` - Second factor after a successful password login (`req.session.pendingTotp`); accepts a 6-digit TOTP code or a recovery code, same rate limiters as `/login`. Not required after a passkey login, which already counts as MFA-equivalent

- `/admin-password` - Change the admin password (admin only, no old-password re-entry — see `lib/password-store.js`)
- `/admin-username` - Change the admin username (admin only, used by the password login form; not by passkey login — see `lib/username-store.js`)
- `/totp/setup`, `/totp/confirm`, `/totp/disable` - Set up/confirm/disable the TOTP second factor (admin only, see `lib/totp-store.js`); `/totp/confirm` returns a set of one-time recovery codes exactly once
- `/admin/logs` - Event-log dashboard (admin only, see `lib/routes/event-log.js`): KPIs, timeline by severity, distribution by module, filterable colour-coded table; `/admin/logs/:id` (detail page, `?partial=1` for the `<dialog>` in `public/js/event-log.js`), `/admin/logs/export.csv|json`, `/admin/logs/settings` (retention/archive rules, `POST` to save), `POST /admin/logs/purge`, `/admin/logs/archives/:file` (download, `POST …/delete`)

- `/admin/backups` (`POST`) - Manually trigger a database backup (admin only, see `lib/backup-store.js`); `/admin/backups/:filename/download` (`GET`) and `/admin/backups/:filename` (`DELETE`) manage individual backups, `:filename` guarded by `safeBackupName()` like the other admin-generated-ID routes. `/admin/backup-settings` (`POST`) updates the schedule (interval/retention/enabled) and re-arms the background timer immediately, no restart needed. `/admin/backups/:filename/restore` (`POST`) is the destructive one — requires a body `{ confirm: filename }` matching exactly, verifies the backup's checksum, takes an automatic pre-restore safety snapshot, then swaps the live database file and deliberately exits the process so the configured restart policy reloads it against the restored data

- `/download-zip` - Bulk download of several selected files as one streamed ZIP (public, same rate limiter as `/download`; see `lib/zip-stream.js`). - `/search` and `/admin-search` - Real-time file filtering
- `/support` - Public entry page of the support portal (`/contact` redirects here): knowledge-base search and published articles by category, plus register/login or (logged in) "Neues Ticket"/"Meine Tickets"; `/support/articles/:slug` (published only — an active admin session also sees drafts, and its views don't count), `/support/articles.json?q=` (suggestions for `public/js/kb-suggest.js`, poll rate limiter)
- `/account/register`, `/account/verify`, `/account/resend-verification`, `/account/login`, `/account/logout`, `/account/forgot`, `/account/reset`, `/account/settings*`, `/account/confirm-email`, `/account/export`, `/account/delete` - Customer accounts (see `lib/routes/account.js`)

- `/admin/tickets/new` (`?customer=<id>`, `?file=`) - the support opens a ticket for a verified, non-disabled customer; `/admin/tickets/:number/merge` (`{ target, confirm: '1' }`) merges this ticket into another one of the same customer; `/admin/tickets/:number/split` (`{ messageIds[], subject, priority, categoryId, confirm: '1' }`) moves selected messages into a new ticket; `/admin/tickets/:number/snooze` (`{ preset | until, note }`, `until` as `datetime-local` wall time) and `/unsnooze`, plus bulk actions `snooze:<preset>`/`unsnooze`; `/admin/ticket-settings/sla`; `/admin/kb*` (article list, `/new`, `/:id` edit with server-side preview via `action=preview`, `/:id/publish`, `/:id/delete`); `/admin/reports` (`range=30|90|365` or `from`/`to` dates, wall time in `APP_TIMEZONE`) - all `checkAuth`-gated

## Security

`server.js` is hardened against the common web risks; keep these in place when editing:
- **Secrets**: no functional defaults — `ADMIN_PASSWORD`/`SESSION_SECRET` are random-generated if unset, and either way (set or generated) persisted to the database on the very first `start()` (see "Bootstrap-once env vars" above). The password is compared timing-safe via SHA-256 + `crypto.timingSafeEqual` before a persisted hash exists, `scrypt` after
- **helmet** sets CSP (`'self'` only, `data:` for images), `frame-ancestors 'none'`, `nosniff`, `same-origin` referrer policy; `x-powered-by` is disabled
- **CSRF**: `sameSite: 'strict'` cookie plus a same-origin (Origin/Referer host == Host) check on every POST/PUT/PATCH/DELETE
- **Session**: `httpOnly`, `sameSite: 'strict'`, `secure` when prod or behind a proxy; regenerated on login (anti-fixation). Cookie name `iso.sid`, backed by `SqliteSessionStore` (`lib/session-store.js`), not the default in-memory store. `TRUST_PROXY` numeric = hop count. The cookie's own `maxAge` (24h) is a fixed absolute ceiling from login, separate from the idle timeout below
- **Admin idle timeout**: `checkAuth` in `server.js` tracks `req.session.lastActivity` and destroys the session (DB row + cookie) the first time a logged-in admin makes a request more than `ADMIN_IDLE_TIMEOUT_MS` (10 minutes) after their last one, redirecting to `/login?idle=1` (or a JSON 401 for API-style callers) instead of `next()`. This is independent of the 24h cookie `maxAge` above — an idle admin is logged out long before that absolute ceiling — and only ever checked/updated on `checkAuth`-gated routes, not on every request. Overridable via the `adminIdleTimeoutMs` option to `createApp()` for tests; logged to the audit log as `session_idle_timeout`. `public/js/idle-timer.js` mirrors this bank-style in the UI: a countdown badge next to "Abmelden" in `partials/navbar.ejs` (reads the timeout from `app.locals.adminIdleTimeoutMs`, wired into every render), reset to the full window by real click/key/mouse/touch activity, which — throttled to at most once/minute — also pings `GET /admin/ping` (`checkAuth`-gated, no-op body) to keep the *actual* server-side session alive; hitting zero client-side navigates to `/logout`. `heartbeat.js`'s automatic 20s poll of `/admin/partials/listing` is deliberately exempted from extending `lastActivity` (via the `X-Idle-Background` request header, checked in `checkAuth`) — otherwise a tab merely left open, with nobody at the keyboard, would keep the session alive forever and defeat the whole feature
- **Rate limit**: `express-rate-limit` on `/login` (10 / 15 min, plus a global backstop — see below) and on `/download` (60 / min per IP; range requests aren't double-counted as separate downloads)
- **Filename safety**: `safeIsoName()` (basename + allowlist regex + `.iso`) guards `/upload`, `/delete`, `/download` and the chunked-upload's `name` field; `safeUploadId()` guards the `:id` path param on every `/upload/:id*` route
- **Uploads**: `uploads/` is NOT served statically — only via `/download` with type check; multer temp dir and the chunked-upload `.part` files (session bookkeeping is a DB row, see `lib/chunked-upload.js`) live in `tmp-uploads/` (outside web root), both capped by `MAX_FILE_SIZE_MB`. Checksums, download counts and every other credential/metadata table live in `data/iso-share.db`, entirely outside `uploads/` and never served directly
- Errors are caught by a final handler that never leaks stack traces (it records them as `unhandled_error` with stack and request id in the event log instead)
- **Event log**: `/admin/logs*` is admin-only. What it stores is personal data (IP, user agent), so: never the query string, never SQL parameters, session ids only as a truncated hash, payloads through `redact()`, and every retention period shown in the privacy policy. Security-relevant rejections are recorded (`ip_blocked`/`rate_limit_global` — only the first blocked request per window, so an attacker can't flood the log —, `csrf_rejected`, `api_auth_failed`, `*_login_failed`). Don't log message bodies, passwords or tokens into payloads
- **Startup config check**: in production the app refuses to start on an unsafe deployment config (see `lib/config-check.js`) — don't downgrade those errors to warnings
- **Docker image**: `.dockerignore` must keep `data/`, `uploads/`, `tmp-uploads/`, `*.db` and `.env*` out of the build context — a local database contains the password hash, session secret, TOTP secret and customer data. The app code in the image belongs to root; only `uploads/`, `tmp-uploads/` and `data/` belong to the `node` user. `docker-compose.yml` binds the app to `127.0.0.1:3000` only; TLS is terminated by Caddy (`--profile tls`, `Caddyfile`) or the operator's own proxy. `test/production.test.js` asserts these deployment invariants
- **Disk space**: `/upload/init`, `/api/v1/uploads` and the multipart `/upload` (via `Content-Length`, before multer reads the body) reject with `507` when the announced size plus the outstanding bytes of all other upload sessions plus `MIN_FREE_DISK_MB` don't fit — checked for `tmp-uploads/` and `uploads/`, each filesystem once (`statfs` + device id; skipped if `statfs` is unavailable). A full volume would otherwise also take down SQLite writes. `cleanupStale()` also removes multer's leftover temp files older than the TTL after a crash
- **All request-path filesystem access is async** (`fs/promises`); no `*Sync` call runs inside a handler, so a large `uploads/` can't block the event loop. The upload move uses `rename` with a `copyFile`+`rm` fallback for `EXDEV` (temp dir and `uploads/` on different mounts, e.g. a Docker bind mount) — see `lib/move-file.js`
- **Login brute-force** is capped two ways: per-IP (`express-rate-limit`, failures only) and a global backstop keyed to a constant, so a spoofed `X-Forwarded-For` (when `TRUST_PROXY` is set without a real proxy) can't mint fresh buckets. Only enable `TRUST_PROXY` behind a proxy that overwrites `X-Forwarded-For`
- **Chunked-upload protocol**: a `PATCH` is only accepted when its `Upload-Offset` header equals the session's real on-disk offset, and the server never writes more bytes than the size announced at `init` — both close off ways a client could otherwise corrupt or oversize the assembled file
- **Passkeys**: additive, not a replacement — the password form is always the fallback. A passkey can only be registered by an already-authenticated admin (no separate bootstrap route); `/webauthn/login/options` and `/webauthn/login/verify` are public but share the exact same `loginLimiterGlobal`/`loginLimiterPerIp` instances as `/login`, so an attacker can't double their brute-force budget by alternating routes. `rpID`/`expectedOrigin` are derived per-request from `req.get('host')`/`req.protocol` (same inputs as the CSRF `sameOrigin` check) rather than a separate env var — a passkey is therefore bound to the hostname it was registered under
- **Password change** (`/admin-password`): checkAuth-gated only, deliberately without re-entering the current password — the whole point is recovering from a forgotten one, and a valid session already implies full admin access regardless. Hashed with `scrypt` (salted, promisified so it doesn't block the event loop), not the plain `SHA-256` used for the `ADMIN_PASSWORD` env-var comparison — that one is fine unsalted since it's not user-chosen/persisted, but a user-settable password gets the stronger, deliberately slow KDF
- **Username check** (`/login`): a wrong username and a wrong password get the exact same generic error ("Benutzername oder Passwort falsch") — distinguishing them would let an attacker enumerate the username. `passwordMatches()` is always awaited even when the username is already known to be wrong, so a mismatched username can't be inferred from a faster response. Both `/admin-password` and `/admin-username` share the same async-form + `<dialog>`-modal pattern in `public/js/account-forms.js`, with a plain-form no-JS fallback (inline error / silent redirect) preserved for both
- **TOTP second factor**: the session is regenerated right after the *first* factor (password) succeeds, before `/login/totp` is even reached — an attacker who somehow knew the pre-login session id can't ride it through to a fully authenticated session just because TOTP was still pending. `/login/totp` and `/totp/confirm` share the exact same rate limiters as `/login`, for the same anti-doubling reason as the passkey routes. Recovery codes are single-use, checked with a `timingSafeEqual` loop, and hashed with plain SHA-256 rather than `scrypt` — unlike the admin password they're server-generated and already high-entropy, so a slow KDF buys nothing (same reasoning as `PASSWORD_HASH` for the env-var password)
- **Bulk routes** (`/download-zip`, `/delete-bulk`): every name in the `{ names: [...] }` body goes through the exact same `safeIsoName()` as the single-file routes — a batch of names is not a new trust boundary. `/download-zip` stays public (like `/download`) and shares its rate limiter; `/delete-bulk` is `checkAuth`-gated like `/delete`
- **Ticket system**: customers and the admin are separate trust boundaries: `req.session.customerId` vs `req.session.loggedIn`, checked only by `checkCustomer` resp. `checkAuth`; both logins `regenerate()` the session. A customer only ever sees own tickets: `getForCustomer()` makes a foreign ticket indistinguishable from a missing one (same 404), `/attachments/:id` re-checks ownership and hides attachments of internal messages. Registration, forgot-password and resend-verification answer identically whether or not the address exists (the mailbox owner gets an "account exists" mail instead), with a scrypt round on the existing-address path so timing matches; registration keeps the honeypot. Password change/reset, disabling and deleting destroy the customer's other sessions (`SqliteSessionStore.destroyForCustomer()`). Rate limits: `accountLimiters` (register/forgot/resend/reset), separate `customerLoginLimiters` (own buckets so customer failures can't drain the admin login backstop), `ticketWriteLimiters` (per IP, plus a global backstop high enough that one account with many IPs can't lock everyone out) and `ticketWritePerCustomer` (30/h keyed on the customer id — the real brake), plus at most 20 new web tickets per account and day. Attachments: magic-byte type check, served with `nosniff` and `default-src 'none'; sandbox`. Message text is escaped before linkifying (`formatMessage()`); mail HTML escapes all user input. Links in mails come only from `PUBLIC_URL`. Inbound mail requires an HMAC-signed thread reference plus the account's exact sender address. `safeNextPath()` blocks open redirects after login; bulk actions only return to `/admin/tickets`
- **Ticket extensions**: a new ticket by mail requires `IMAP_AUTHSERV_ID`, a verified account *and* DKIM/DMARC confirmed by the own mail server's topmost `Authentication-Results` header (`lib/mail-auth.js`) — the From address alone is forgeable; rejections are silent (no backscatter). A customer's `isoFile` must be an existing file (`safeIsoName()` + listing), the admin may keep a name of a deleted one. Merging only within one customer account, so it can never leak a thread to another customer; the merged source's URL 301s only if the target belongs to the same customer. Knowledge-base HTML only ever comes out of `lib/markdown.js` (escape first) and is the one place a view uses `<%- %>` on user-authored text — keep it that way. Draft articles are public 404s. Report and KB admin routes are `checkAuth`-gated
- **`/api/v1` token auth**: completely separate trust boundary from the session — `checkApiToken()` never reads `req.session`, so a stolen/forged session cookie grants zero `/api/v1` authority, and a leaked token grants zero session/admin-UI access either way. A token is created only via `POST /admin/api-tokens` (`checkAuth`-gated, no API-reachable self-issue path, same bootstrap reasoning as passkeys) and carries `scopes: ['read']`/`['write']` checked per route. Because of this separation, the global CSRF `sameOrigin` check is skipped for `/api/v1/*` — a cross-site request riding the victim's cookie still can't produce a valid `Authorization: Bearer` header, so the check would only false-positive-block legitimate script/CI clients that don't send a same-origin `Origin`/`Referer`. Failed token checks share a login-style two-tier rate limiter (`apiAuthLimiterPerIp`/`apiAuthLimiterGlobal`, defense-in-depth — a 256-bit token isn't brute-forceable); all of `/api/v1` additionally shares one generous `apiLimiter` (300/min) against runaway scripts. Error responses carry a stable `code` field (`missing_token`, `invalid_token`, `insufficient_scope`, `not_found`, …) alongside the German `error` message, and the 404/500 handlers branch to JSON for any `/api/v1/*` path instead of the plaintext used elsewhere
